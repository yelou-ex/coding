 CAPE ANSWER 耗时 × 查询关键词数 Q —— 实测记录
 记录时间：2026-09-30
 测试类：com.fusepir.rgsw.CapeEndToEndNative（ANSWER = native 真 SEAL C++）
========================================================================

★ 一句话结论
  ANSWER 耗时与查询关键词数 Q 无关：Q 从 2 增到 20（×10），耗时变化在 ±4%（噪声范围内），
  单元数恒为 120。这是 CAPE 论文那句 "checking all remaining query terms jointly
  without introducing per-keyword query or computation overhead" 的实测证据。

  但必须同时看第 5 节：本次只变了"查询侧"的 Q，没有变数据库，所以 Q>2 时
  合取判定并不成立 —— 这组数据只证明"时间不随 Q 变"，不证明"Q 大时能正确命中"。


────────────────────────────────────────────────────────────────────────
 1. 本次实测的规模（所有 Q 共用同一套参数）
────────────────────────────────────────────────────────────────────────

  HE 层（原生 SEAL 4.0.0，bfv）
    N（环维度）         4096
    t（明文模数）        65537
    base                2^16 = 65536
    levels              5
    工作素数             2 个
    q（工作模数）         72 bit
    系数模数总位宽        109 bit（声明 3 个素数，含 q_last）

  CAPE 结构
    k（BFF 位置数）       3
    C（列数）            4
    R（行数）            16          → R×C = 64 槽
    d（LWE 维数 = 盲旋转轮数） 16
    ε_BF                2^-6  ← 【玩具值】，论文是 2^-20
    ℓ_BF                18
    h（Bloom 哈希数）     5
    maxValues            2
    B_pay               2 + maxValues×(1+ℓ_BF) = 40
    ANSWER 单元数         k × B_pay = 3 × 40 = 120

  "数据库"
    3 个手写关键词（K_1/K_2/K_3）
    3 个值（11/22/33），每个值关联 1~2 个关键词
    载荷 = 指纹(1) ‖ 值个数(1) ‖ 每个值[值(1) ‖ ℓ_BF 个 Bloom 位]

  ⚠️ 这是一个**玩具规模**：3 个关键词、64 个槽。对照见第 4 节。


────────────────────────────────────────────────────────────────────────
 2. Q 扫描实测结果（N=4096, d=16, C=4, k=3, B_pay=40）
────────────────────────────────────────────────────────────────────────

   Q      τ         b_qry 覆盖关键词数     ANSWER 单元数      ANSWER 耗时
  ─────────────────────────────────────────────────────────────────────
   2      3              1                    120             5 631 ms
   5     12              4                    120             5 815 ms
  10     15              9                    120             6 030 ms
  20     18             19                    120             5 786 ms
  ─────────────────────────────────────────────────────────────────────
   波动范围                    5 631 ~ 6 030 ms（±4%，属运行噪声）
   单元数                        恒为 120
   趋势                         **无趋势**（Q ×10，耗时不变）

  Q 的定义（CAPE Algorithm 2）：
    QUERY(pp, sk, K = (K_1, …, K_Q))
      K_1        是【锚】，用来做 PIR 检索
      K_2..K_Q   这 Q−1 个只当作字符串散列进一个 Bloom 过滤器 ⇒ b_qry
      τ = ‖b_qry‖₁

  ⚠️ 实际测过的只有 Q = 2 / 5 / 10 / 20 四个点。
     **未测**：Q = 1, 3, 4, 6, 7, 8, 9, 11~14, 16~19。
     要补测：.\run-mpc4j.ps1 -Class com.fusepir.rgsw.CapeEndToEndNative 4096 16 <Q>

 3. 同一份实现在不同 N 下的 ANSWER 耗时
────────────────────────────────────────────────────────────────────────

   规模      工作素数 / q      levels    单轮 CMUX      ANSWER（120 单元）
  ────────────────────────────────────────────────────────────────────────────
   N=4096       2 / 72 bit         5       ~3 ms          5 631 ~ 6 030 ms
   N=8192       4 / 174 bit       11      ~36 ms             69 960 ms
   N=16384      8 / 389 bit       25      259 ms         未跑四步（只验过正确性）

  N 从 4096 提到 8192 ⇒ ANSWER 慢 11.7 倍。放大来自三处相乘：
    N ×2  ×  levels ×2.2  ×  工作素数 ×2

  另：N=16384 上单轮 CMUX = 259 ms，正确性 4/4 PASS（RGSW(1)⊗ct=ct 精确 0 错位、
  RGSW(0)⊗ct=0、盲旋转 one-hot→one-hot），但没跑四步 —— 按趋势是分钟级。

────────────────────────────────────────────────────────────────────────
 5. 必须挂上的边界（不要拿这组数据做超出范围的结论）
────────────────────────────────────────────────────────────────────────

 (1) 命中判定在 Q>2 时不成立 —— 这是预期的，不是 bug
     本次只把"查询侧"的 Q 加大（造 Q 个字符串 K_1..K_Q 去散列），
     **数据库没变**：锚的 value 11 的 Bloom 过滤器仍然只覆盖 {K_1, K_2}。
     所以 Q>2 时 ⟨b_qry, b_v⟩ 必然 < τ。测试里对此只打印 [info]，不断言命中；
     负对照 4.5/4.6（与 Q 无关）也在 Q>2 时跳过。
     ⇒ 本组数据证明的是「时间与 Q 无关」，**不是**「Q 大时 CAPE 能正确命中」。

 (2) τ 在 ℓ_BF=18 上瞬间饱和 ⇒ Q=20 那一档是退化的
     Q=20 时 b_qry 覆盖 19 个关键词 × h=5 = 95 次插入打到 18 位上 ⇒ τ=18（全满）。
     "要求候选命中全部 18 位"是极强的判据（假阳性极低、假阴性极高），
     不能代表论文场景（论文 ℓ_BF ≈ 5075，τ 增长慢得多）。

 (3) 本组的 B_pay = 40 是**玩具 ε_BF 的产物**
     B_pay = 2 + maxValues×(1+ℓ_BF)，而 ℓ_BF 由 ε_BF 决定。
     论文 ε_BF = 2^-20 ⇒ ℓ_BF ≈ 5075 ⇒ B_pay ≈ 6.65×10^5
     ⇒ 单元数 = k × B_pay ≈ 2×10^6，按 47 ms/单元算是**小时级**。
     **⇒ 换到论文参数，这套成本结构完全不成立。**

 (4) native 用的是 base CAPE 选择子
     即 C 个独立 one-hot 密文。Java 侧当前提交版本用的是 EXPAND 压缩选择子
     （12 个密文 → 3 个，但服务端 +8.5%）。两者不能混：
     EXPAND 输出 Enc(C)，必须把 α = C^{-1} mod t 折进明文表。

 (5) BLooM 打分口径不同
     Java 版是**同态**打分（CtCtMul + Galois 折叠）；
     native 版是**明文侧**算（因为回环时锚载荷已解出）。
     ANSWER 计时区间里两边都不含打分，所以这一轴没污染速度对比。

 6. 与另外两条外部基准的规模差（决定这些数字能不能比）
────────────────────────────────────────────────────────────────────────

  参数            本次          论文 CAPE              BKPIR（2MB 那份）
  ─────────────────────────────────────────────────────────────────────────
  N              4096          16384                  8192
  工作素数 / q     2 / 72 bit    8 / 389 bit            5 / 218 bit
  levels           5             25                     —
  噪声预算         ~51 bit       —                      153 bit
  关键词数          3            n（MovieLens 1475）    128
  项目/槽            64           —                      8192
  数据库           ~0             GB 级                  2 MB
  B_pay            40           ≈665 092               —
  ε_BF             2^-6（玩具）   2^-20                  —
  ANSWER 单元数     120           k × 6.65e5             —
  ANSWER 耗时       5.9 s         论文 Table 3 = 3.00 s*  8.48 s（单关键词）

  * 论文 Table 3 的读数来自 OCR，且 15 行数值几乎相同 —— 早先已标为**可疑**，
    不建议当基线。

  单次查询的 CMUX 次数 = k × B_pay × d：
    本次      ：3 × 40 × 16          = 1 920 次    → 5.9 s
    论文规模  ：3 × 665 092 × 512     ≈ 1.0×10^9 次 → 相差约 5×10^5 倍
  ⇒ **本组的 5.9 s 与论文的 3.00 s 完全不可比。**
