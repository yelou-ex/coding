## 一、结论先说：没有达到，差约 2–3 个数量级，而且**瓶颈不在列选择**

| 项 | 数值 |
|---|---|
| 单次 ANSWER 单元数 | `k × B_pay` = 3 × 40 = **120** |
| 实测 ANSWER 总耗时（`CapeEndToEnd4`，N=4096, d=16） | **50 078 ms** ⇒ 417 ms/单元 |
| 独立复测单单元（预热后，中位数） | **253.7 ms** |
| 其中 **盲旋转**（d=16 轮 CMUX） | **249.4 ms = 98%** |
| 其中列选择（C=4 次 `CtPtMul` 全部三段） | **3.6 ms = 1%** |
| 其中 `SampleExtract_0` | 0.5 ms |
| 单轮 CMUX 单价 | **15.6 ms** |
| 每次查询的 CMUX 总数 | 120 × 16 = **1920** ⇒ 约 30.0 s |

**列选择只占 1%。** 这一点直接推翻了"优化列选择能提速"的直觉 ——
SealPIR §3.2 / OnionPIR §4.3 的 `EXPAND`（单子密文扩成 one-hot）解决的是
**P0-3（Pack）与 P2-7（列选择器形态）的正确性/功能问题，对速度收益约等于 0**。

逐段证据（预热后中位数）：

```

列选择② 明文构造 + NTT            :      1.0
列选择③ multiplyPlain + add       :      0.8
盲旋转（16 轮 CMUX）              :    249.4   ⇒ 单轮 15.6 ms
SampleExtract_0                   :      0.5
────────────────────────────────────────────
实测单元合计                       :    253.7
```

## 二、为什么慢：不是算法慢，是**纯 Java 实现慢**

### 2.1 算法侧是对的 —— 单元数与论文结构一致

`CapeEndToEnd4` 的 ANSWER 严格按 Algorithm 2 第 5–7 行：
每个 `(a, b)` 做 1 次列选择 + 1 次盲旋转 + 1 次 `SampleExtract_0`。
**论文 CAPE 也是 `k × B_pay` 次盲旋转**，我们一步不多。
所以差距**不来自串行/冗余的算法结构**。

### 2.2 实现侧是 300–500× 的单价差

MPC4J 的 SEAL 是**纯 Java 移植**：`externalProduct` / NTT / gadget 分解
全部跑在 `long[]` 上由 JIT 生成标量代码，没有 AVX-512 向量化，也没有
native 的 lazy reduction / 预计算表。原生 SEAL 在 N=4096 上一次
`external_product` 量级是几十微秒，我们是 **15.6 ms/CMUX**。

### 2.3 二阶因素：gadget 参数是随手选的，没扫过

`new Mpc4jRgsw(n, 65537L, 0, 1 << 16)` ⇒ `base = 2^16`、`levels = 5`
（见探针输出头部 `base=65536, levels=5`）。
这意味着**每一轮 CMUX 要把累加器分解成 5 个 digit**，即 5 次密文 NTT +
5 次 external product。base/levels 从未做过扫描 —— `base=2^16` 是当初能跑通就定的。

## 三、缺在哪儿（按收益排序）

1. **缺 native 后端**（唯一能拿回 2–3 个数量级的路）
   `coding/native-jni/` + `tools/SEAL-4.0.0` 已有底子，但未接通主链路。
2. **缺 gadget 参数扫描**：`base` / `levels` / 素数位宽三者耦合，
   在纯 Java 下单轮 CMUX 的成本与 `levels` 近似线性，值得扫一遍。
3. **缺可靠的论文基线**：论文 Table 3 的 "CAPE online = 3.00 s" 是从
   `out_*.txt` OCR 出来的，且 15 行数值几乎完全相同 —— **可疑，不能当基线用**。
   用它算出来的"差多少倍"只能当量级参考。

---

## 四、必须如实标注的两点存疑

1. **417 ms/单元 vs 253.7 ms/单元，1.6× 的差我没能归因。**
   预热已排除：逐单元序列 `254 250 265 256 ... 249 243 278 436`，
   第 1 个单元 254 ms、中位数 249 ms ⇒ 预热放大 **1.02×**，从一开始就是稳态。
   最可能是 `CapeEndToEnd4` 现场堆压力/GC（它同时持有明文表、数据库、
   `sample[3][40][2][4097]` 等，且只给 `-Xmx4g`），但**我没有测量证实**，
   所以本记录以独立的 253.7 ms 作为可信分解，417 ms 作为现场值并列。
2. **"2–3 个数量级"是从不可靠基线推出的量级判断**，不是精确倍数。
   可靠的说法是：*单价*上我们比原生 SEAL 慢约 300–500×（15.6 ms vs 数十 µs）。

## 五、对既有计划的修正

- ❌ 原拟「把列选择升级成 SealPIR/Chen 的 monomial + `EXPAND`」**不要当成性能优化项推**。
  ✅ 它应当只挂在 **P0-3（Pack 接通）** 与 **P2-7（选择子形态符合论文）** 下。
- ✅ 性能主线只有一条：**native 后端**。在此之前，任何算法侧微调都在 1% 的量级里挪。
