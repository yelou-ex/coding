# MPC4J / SEAL 里能用来加速盲旋转的东西（2026-09-30）

> 问题：**MPC4J 与 SEAL 的代码里有能提升盲旋转速度的吗？**
>
> 已实测的现状（见 `ANSWER单元性能剖析…md`、`CmuxProfile`）：
> 单轮 CMUX = **15.55 ms**，其中
> - **① 切段 `decompose × 2`（BigInteger CRT）= 6.25 ms（45%）** —— 我们自己的代码
> - **② 10 次 `multiplyPlainNtt` + 累加 = 7.54 ms（55%）** —— 0.75 ms/次
> 盲旋转占 ANSWER 的 **98%**。

---

## 〇、先说结论

1. **两个库都没有 RGSW / CMUX / external product。** SEAL 的 API 里根本没有 RGSW，MPC4J 也没有。
   ⇒ **不存在"调一个更快的盲旋转"这回事**，盲旋转 100% 是我们自己的代码。
2. **但 MPC4J 把 SEAL 的 RNS / NTT 底层暴露成 `public` 了**，我们的 CMUX 走的是上层
   `Evaluator.multiplyPlain`，把这一层整个绕过去了。**这是可省的部分。**
3. **附带好处**：走 RNS 域能**解除 `base ≤ t/2` 的枷锁** —— 那是 `fast plain lift`（mod t）带来的，
   不是密码学约束。解掉它，`base`/`levels` 才真正可以扫（也才是那两篇论文的噪声分析能派上用场的地方）。
4. jar 里**没有** JNI / native Evaluator 绑定（类名匹配 `Native`/`Jni`/`JNI` 全无）——
   与已记录的"native 侧只有协议级接口"一致。

## 二、主路：用 RNS 域点乘替掉 `Evaluator.multiplyPlain`

### 现在每次明文乘在做什么
```
new Plaintext(n) → 填 4096 个 Z_t 系数
  → transformToNttInplace(pt, parmsId)     ← 含 **fast plain lift**：校验 + plainUpperHalfIncrement
                                              嵌入 + NTT（比普通 NTT 重）
  → Evaluator.multiplyPlain(ct, pt, dst)   ← 含 parmsId/形态校验层
```
（`Mpc4jRgsw:431 multiplyPlainNtt`）

### 单价差
| 路径 | 单价 |
|---|---|
| `Evaluator.multiplyPlain` 本体（NTT 域点乘） | ≈ **0.2 ms**（`AnswerUnitProfile`：4 次共 0.8 ms） |
| 我们的 `multiplyPlainNtt`（含上面整套包装） | **0.75 ms** |
| **⇒ 包装层 ≈ 0.55 ms/次；每轮 CMUX 10 次 ⇒ ≈ 5.5 ms = CMUX 的 35%** | |

⇒ 把这 10 次换成"切段数字直接 NTT 进密文的 RNS 布局、逐素数点乘"，可省掉
`Plaintext` 对象、fast plain lift、`Evaluator` 校验层。**目标：CMUX 15.55 → 约 8~10 ms。**

### 关键副作用：解除 `base ≤ t/2`
现在 `base = 2^16` 顶在平衡位窗口 `±(t−1)/2 = ±32768`（`Mpc4jRgsw:389-393` 会抛），
`levels = 5` 由 `B^levels/2 > q(≈2^72)` 决定 —— 于是"10 次乘法"看似结构性。

**但那个窗口是 `fast plain lift`（mod t）独有的。** 一旦在 RNS 域做 **mod q** 乘法，
约束消失，`base`/`levels` 才成为真正的可调参数（代价：每轮噪声随 base 增大，
必须用 OnionPIR §2 的 external-product 噪声界来定，d 轮累加）。

> **注意**：native SEAL **也不提供** "ct × mod-q plaintext" 的公开接口 ——
> 它只在 `KeySwitcher` 内部做。所以这条路等于**我们自己补上 SEAL 内部的那一层**。
> 纯 Java、不需要 JNI，但工作量不小，且必须先过噪声关。

## 三、立即可用的小赢

| 项 | 现状 | 改成 |
|---|---|---|
| `Evaluator.multiplyPlainInplace(ct, pt)` | 我们用 3 参数版（`dst`） | 原地版，省 `Ciphertext` 分配/拷贝 |
| `Evaluator.addPlainInplace` / `negateInplace` | 同上 | 原地版 |
| `Evaluator.addMany(Ciphertext[], dst)` | 我们的 `Σ_c` 是一串 `addInplace` | `addMany` 一次搞定 |
| **`decompose` 去 `BigInteger`** | `crtAt` 每个系数一次 `BigInteger` CRT（①，45%） | 只有 2 个工作素数、q ≈ 2^72 ⇒ 用 `long` + `Math.unsignedMultiplyHigh` 的 128 位表示即可。库自己的 `RnsBase.compose` / `getPuncturedProdArray` 就是这个思路（**用预计算 punctured-product 表代替大整数**） |

---

## 四、明确**不可用**的

- **没有现成 RGSW/CMUX/external product**（两个库都没有）。
- **没有面向应用的 native Evaluator 绑定**（jar 里无 JNI 类）。
- `ntt.ModArithLazy` 包私有，不能直接用（但 `NttTool` 的 public 入口已覆盖它）。
- `rns.RnsBase.decompose` 的粒度是**"一个素数一段"**（~2^36/段），
  **不是**我们要的 `base-2^16` 段。所以它**不能直接替换**我们的 `decompose` ——
  它能替换的是"**改成 RNS-gadget 后的**切段"（即上面第二节那条路的一个零件）。

---

## 五、建议顺序（按收益/风险）

1. **`decompose` 去 BigInteger** —— 局部改动、不动算法语义、可立刻量出倍数。盯 ①的 45%。
2. **RNS 域明文乘替换 `Evaluator.multiplyPlain`** —— 盯 ②的 55%，并**打开 base/levels 扫描空间**。
3. **native 后端** —— 唯一能拿 2~3 个数量级的路。

> 两篇新论文（SealPIR / OnionPIR）对第 3 步毫无帮助；它们只在第 2 步"打开参数空间之后"
> 才第一次有意义 —— 因为它们的噪声分析正是用来选 gadget 的。

## 六、① 已执行：切段去 BigInteger（2026-09-30 完成）

**改动**：`Mpc4jRgsw.decompose` 拆成 `decomposeFast`（纯 `long`）/ `decomposeBig`（原 BigInteger，回退）。
快路径条件：**恰好 2 个工作素数 + base 是 2 的幂**（我们的配置恒成立；N=8192 是 4 个工作素数 ⇒ 自动回退）。

算法：Garner 重构 `x = r0 + p0·t1`，其中 `t1 = (r1−r0)·p0^{-1} mod p1` 用
**Montgomery 乘法**（`Math.unsignedMultiplyHigh` 的 REDC）算；`x` 用 `(hi, lo)` 两个 long 表示，
逐段取平衡位只做移位与掩码。

| 指标 | 改前 | 改后 | 倍数 |
|---|---|---|---|
| `decompose` ×2（每轮 CMUX） | 6.25 ms | **0.36 ms** | **17.4×** |
| 切段占 `externalProduct` | 45% | **6%** | — |
| **一次完整 CMUX** | 15.55 ms | **8.08 ms** | **1.92×** |
| **`CapeEndToEnd4` 的 ANSWER（120 单元）** | 50 078 ms | **21 181 ms** | **2.36×** |
| 单单元 | 417 ms | **176.5 ms** | 2.36× |

**ANSWER 的实测倍数（2.36×）高于隔离微基准（1.92×）**，这正好解释掉之前
`ANSWER单元性能剖析…md` 里那条**存疑**：「417 ms/单元 vs 独立复测 253.7 ms/单元，1.6× 说不清」。
根因就是 **BigInteger 每系数产生的垃圾**（2 分量 × 4096 系数 × 每次 CMUX，×1920 次 CMUX/查询）。
去掉后现场值与隔离值的差距从 1.64× 缩到 1.33×。

**正确性保证**：新增差分测试 `DecomposeEquiv`
（`.\run-mpc4j.ps1 -Class com.fusepir.rgsw.DecomposeEquiv 4096 6`），
**3/3 PASS**：快慢路径 **245,760 个（系数×段）值逐位一致**，
外加一条**独立校验**「`Σ d_k·B^k ≡ x (mod q)`」（不经慢路径，防两条路一起错）。

**回归**：Mpc4jRgsw / RgswPolyTest / LweRlweBridge / BlindRotateOps / BlindRotateComplete /
LweRlweConversion / BloomScoring / BloomInnerProductProbe / SampleToPackLink /
AnswerPathMini(2048,4096) / RingPack(8192，走回退) / CapeEndToEnd4 —— **全部通过**。

**② 现在是唯一剩下的 Java 侧目标**：`externalProduct` 里 94% 是那 10 次
`multiplyPlainNtt`（5.88 ms / 8.08 ms），单价 0.59 ms 而 `Evaluator.multiplyPlain` 本体仅 0.2 ms。
