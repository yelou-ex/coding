# P1-1：列选择子改客户端加密 —— **已完成**（2026-10-14）

> **一句话**：论文 A1 QUERY 4-5 的 `q^col_a = RLWE.Enc_{s_R}(e)` 现在**真的实现了** ——
> 客户端把 C 条 one-hot 选择子加密后送上线路，服务器只 `load + multiply_plain`，
> **看不到 `c_a`**。进程内验收 **3 PASS / 0 FAIL**（逐系数一致 + 两条负对照），
> 跨进程线格式验收 **ALL CHECKS PASSED**。
>
> 顺带挖出并修掉了一个**比 P1-1 本身更重要**的老 bug：sealed 路径的「载荷恒 0」
> 不是"没修完"，而是 **JNI 数组类型写错**（见 §四）。

---

## 一、要做什么（论文依据）

```
A1 QUERY  4: e <- (0,...,0, 1, 0,...,0) ∈ {0,1}^C, with the 1 at index c_a
A1 QUERY  5: q^col_a = RLWE.Enc_{s_R}(e)        <-- 选择子是**密文**
A1 ANSWER 5: Acc_{a,b} <- Σ_c CtPtMul(q^col_a[c], P_{c,b}(X))   <-- 表是**明文**
附录 D.2   : "a column selector is indistinguishable by RLWE IND-CPA security"
```

改动前的实现（`nativeCapeAnswerSealed`）收的是**明文** `colIdx[a]`，再在服务端造 one-hot
选择子 ⇒ 服务器直接知道 `c_a`。这正是 `docs/缺陷总表.md` 的 **D13** 里
「`(c_a, r_a)` 两者都可还原」的**前半句**。

## 二、为什么必须在 native 上下文里加密

直觉上"客户端加密"应该能在 Java 打分信道（`Mpc4jRgsw`）里做。**不行**，原因是结构性的：

* 旧路径 `CtPtMul(sel, P)` 的积紧接着进的是 **`blind_rotate`**（d 轮 CMUX，用 RGSW 引导密钥）；
* 列选择子必须与**累加器**在同一个上下文 ⇒ 只能是 native 的 SEAL 上下文。

## 三、做成了什么

### 3.1 native 侧

| 入口 | 作用 |
|---|---|
| `nativeEncryptSealedColumn(h, value)` | 加密**一个**选择子（`value != 0` ⇒ 常数 1，否则零多项式），NTT 域、序列化后 524,401 字节 |
| `nativeEncryptSealedColumns(h, values[])` | 一次 JNI 调用加密 `k×C` 条，路优先、每项前置小端 int32 长度 |
| `nativeCapeAnswerSealedC(...)` | **P1-1 的 ANSWER**：选择子从密文字节流 load，而不是按明文列号自造 |
| `cape_answer_core(...)`（新，内部） | **两种选择子形态共用同一段循环体** |

**参数语义（容易写错，写清楚）**：`value` 是论文那个 one-hot 向量里的**标量 `e_cc`**，
**不是列号**。第 `(a,cc)` 项加密 `e_cc = [cc == c_a]`，**列的身份藏在"哪一项是 1"里**
—— 这正是服务器不允许知道的东西。（我第一版把它写成"one-hot 中 1 的位置"，
那等于把列号又编码进密文语义里，已改回标量语义。）

**共用循环体是刻意的**：验收断言是「密文选择子路径的载荷 == 明文列号路径的载荷」，
只有从选择子到解码之间跑的是**同一份代码**时，这句话才是在测选择子，
而不是在测两份可能各自写错的循环。

### 3.2 Java 侧

| 位置 | 改动 |
|---|---|
| `CapeQuery.Sealed.selBlob` | 新增：列选择子密文流（`null` = 退回基线形态） |
| `CapeQuery.encryptColumnSelectors(ctx, k, C, colIdx)` | 按论文的 `e` 造 `k×C` 个 `e_cc` 并加密 |
| `CapeQuery.encryptSelectorVector(ctx, e)` | 直接加密给定的选择子向量（**负对照专用**） |
| `CapeQuery.toJson` | `colSel` + `colSelLen` 与 `colIdx` **互斥**发出（见 3.3） |
| `CapeScorerWire.bytesToPackedWire / packedWireToBytes` | 7 字节/long 的打包（41 MB 走不了"一字节一数字"） |
| `CapeDemoService.runQuerySealed` | `selBlob != null` ⇒ 走 `nativeCapeAnswerSealedC` |
| `CapeDemoService.parseSealed` | 收 `colSel`/`colSelLen`，与 `colIdx` 二选一 |
| `/api/selftest/column` | **410 → 真实现**（P1-1 的进程内验收） |

### 3.3 为什么 `colIdx` 与 `colSel` 互斥发出

`toJson` 在 `selBlob != null` 时**不写 `colIdx`**。这样「线路里还有没有明文列号」
是一个**可观测的性质**，而不是一句声明 —— 断言 `!json.contains("\"colIdx\"")`
才有内容。相应地，P1-1 形态下服务器回包里的 `colIdx` 是**空数组**（它确实没有）。

### 3.4 线格式：为什么是 7 字节/long，不是 8

`CapeScorerWire.bytesToWire` 是"一字节一个 JSON 数字"。对 211 KB 的 `q_BF` 只是浪费；
对 41 MB 的选择子流会编出 1.2 亿个数字。所以 P1-1 用打包：每 `long` 装 **7** 个字节。
**刻意不用 8** —— 8 字节会产出 ≥ 2⁶³ 的值，而本项目的 `JsonParser` 解成**有符号** `long`，
那样会静默变成负数。

## 四、★ 挖出来的真根因：`sBits` 的 JNI 数组类型写错（比 P1-1 本身更重要）

### 4.1 症状

`selftestSealed()` 在这之前一直是：

```
3. 载荷 valueCount=0 τ=5 前 3 项=[0, 0, 0]
   接受=[]　池内真值=[5706]
4. 答案与池内真值一致: FAIL
```

计划书把它记成「sealed 路径正确性未修完（载荷恒 0）」，`/api/query-sealed` 因此
默认返回 **501** —— 当时的理由是「**一个『返回成功但结果是 0』的接口比一个报错的接口
危险得多**」。那个判断是对的，但它遮住的是症状、不是根因。

### 4.2 根因

```java
// Java 侧（一直没有变过）
public static native long[] nativeCapeAnswerSealed(..., int[] sBits);

// C++ 侧（错的）
jlongArray sBitsArr     // ← 而每个 Java 调用方传的都是 int[]
...
jlong *sb = env->GetLongArrayElements(sBitsArr, nullptr);   // ← 按 8 字节读 int[]！
```

`GetLongArrayElements` 拿到的是 `int[]` 的数据指针，按 8 字节重解释 ⇒ 第 i 个"long"
其实是 `(int[2i], int[2i+1])` 拼出来的。于是：

* **β 是客户端用真比特算的**；
* **bk 是服务端用被读坏的比特建的**；
* 净旋转量变成 `Σ a_i·(s_i^bk − s_i^client) − r_a` ⇒ **载荷恒 0，永久且无报错**。

这一条同时解释了：为什么 `nativeCapeAnswer`（老路径）**没事** ——
它不收 `sBits`，而是内部调 `secret_bits(c, d)`，那条路没有类型转换。

**为什么以前没被抓到**：`nativeCapeAnswerSealed` 的 4 个调用方**全都**传 `int[]`，
所以按 C++ 声明看它"自洽"；而按 Java 声明看也自洽。**只有把两边放在一起看才矛盾。**
对照清单里从来没有"逐参数核对 JNI 类型"这一项。

### 4.3 修法与绊线

```cpp
jintArray sBitsArr
jint *sb = env->GetIntArrayElements(sBitsArr, nullptr);
if (v != 0 && v != 1) throw ...   // ← 绊线：被读坏的数组不可能通过
```

加 `{0,1}` 校验的理由：这一类 bug 的表现是**静默算错**，而不是崩溃。
一条"值域必须合法"的断言能把"静默错"变成"大声错"。

### 4.4 修完的实测

```
3. 载荷 valueCount=3 τ=5 前 3 项=[2633369476, 3, 5706]
   接受=[5706]　池内真值=[5706]
4. 答案与池内真值一致: PASS
=== 4 PASS / 0 FAIL ===
```

（顺带修了这段自检自己的计数器 bug：原来写的是
`pass += match ? 1 : 0; fail += match ? 1 : 0;` —— 两项都加，
于是永远打印 `N PASS / N FAIL`，与逐条断言自相矛盾。**计数器自己错了比断言失败更隐蔽**。）

**⇒ `/api/query-sealed` 的 501 闸门随之翻转**：默认放行，
只保留 `-Dcape.sealed=false` 显式关闭（这条路现在要过 41 MB，内存吃紧的机器需要能关）。

## 五、验收证据

### 5.1 进程内验收（`/api/selftest/column`，也是 `-Dcape.selftest=true` 的启动自检）

```
1. 基线（服务器按明文列号自造 one-hot）载荷: [2633369476, 3, 5706, 1] ...
   基线 colIdx（服务器看得到）: [5, 5, 5]
2. P1-1（客户端密文选择子）载荷:          [2633369476, 3, 5706, 1] ...
   [断言 1] 与基线逐系数一致: PASS
   选择子流 40903590 字节（k=3 × C=26 条，每条 524401 字节），加密 330 ms，
   ANSWER 50875 ms（基线 51796 ms）
3. [负对照] 第 0 路换列 5 -> 6，载荷必须不同: PASS
   （前 4 项 [3603033330, 1894695358, 1873957785, 2825288475]）
4. [负对照] 全零选择子 ⇒ 载荷必须全零: PASS
=== 3 PASS / 0 FAIL ===
```

**为什么三条缺一不可**：断言 1 单独看可能因为"两边都是 0"而空过
（**这正好就是它当时抓到的东西** —— 第一次跑时断言 1 PASS、负对照 3 FAIL，
一眼看出下面那层是坏的）。负对照 3 排除"载荷与选择子无关"，负对照 4 排除"选择子没起作用"。
**这一轮的实际经验：断言给出绿灯，负对照给出真相。**

**两次独立运行的读数**（同一台机器、同配置；引数必须带机器状态，这是本仓库的规矩）：

| 项 | 第 1 次 | 第 2 次（最终） |
|---|---|---|
| 基线载荷 / P1-1 载荷 | `[2633369476, 3, 5706, 1]`（两边相同） | 同左（两边相同） |
| 选择子加密 | 333 ms | 330 ms |
| ANSWER（P1-1） | 52,865 ms | 50,875 ms |
| ANSWER（基线） | 52,780 ms | 51,796 ms |
| 单元标定 | — | 283.9 ms/单元（**同配置两次运行之间抖动到 190~304 ms**） |

> ⇒ 结论只用**方向性**的读法：`load` 78 条密文的开销**落在机器抖动里**，
> 不能声称"P1-1 比基线快 900 ms"。

## 六、★ 新发现的协议边界：选择子必须与**解码者**同一把秘密

**这一条是本轮第二个值得单独记的收获，而且它推翻了我第一版跨进程验收的断言。**

第一版 `CapeColumnSelWireTest` 让客户端**新建自己的上下文**加密选择子，理由是
「选择子进的是 `multiply_plain(ct, pt)`，服务器只把它当一条密文用」。那句话对，
**但结论错了一半** —— 实测 A ≠ B：

```
A: P1-1（colSel 密文流）载荷前 4 项 [2603260353, 2024078321, 1386151961, ...]
B: 基线（colIdx 明文位置）载荷前 4 项 [71646159, 3090238986, 3133393288, ...]
```

原因是**回环的 DECODE 那一步**：`cape_answer_core` 末尾用 `c->decryptor`
（**服务端的秘密密钥**）解出载荷。而 `multiply_plain` **不改变密文的密钥**：
在谁的秘密下加密，整条累加器就永远在谁的秘密下。客户端用自己的上下文加密
⇒ 累加器变成"客户端秘密下的密文" ⇒ 服务端那把密钥解出来就是垃圾。

**正确的要求是**：选择子必须与**最终解码者**同一把秘密。

| 部署形态 | 解码者 | 选择子应该用谁的上下文加密 |
|---|---|---|
| 本项目的**单进程回环** | 服务端（`c->decryptor`） | **服务端上下文**（所以进程内验收必须用 `ctxHandle`） |
| **真两方部署** | 客户端（它持有 `s_R`） | 客户端自己的上下文 |

⇒ 这不是 P1-1 的缺陷，是**回环捷径**的直接后果，与 `CapeSealedFlowTest` 里
「β 需要与累加器同一秘密」是同一类约束（那个是**加密**侧，这个是**解密**侧）。

**对 P1-1 结论的影响（必须一起说）**：P1-1 关掉的是
**线路上那条明文 `c_a` 信道**（已实测：`colIdx` 不在出站 JSON 里）；
但回环里"客户端"与"服务器"共享上下文与秘密，所以这**不是**密钥隔离，
只是**数据流**与论文一致。真部署里它才同时是密钥隔离。

## 七、⚠️ P1-1 **没有**解决的那一半

**`r_a` 仍然可被服务器还原**，而且这不是实现问题，是**结构问题**：

```
beta = <a, s_L> + r_a
```

回环里客户端的 `sBits` **就是**服务端的秘密比特（`bsk` 就是这么建的、
也是它能在回环里跑通的原因），所以服务器能自己算 `<a, s_L>` 再减掉 ⇒ `r_a` 唾手可得。
可执行的泄露演示见 `CapeAlgorithm2Diag` 的负对照 **N5**。

要遮住它必须引入**真正独立的 `s_L` 与噪声**，也就是 **P1-2**。
**⇒ P1-1 关掉了 `c_a`，`r_a` 那一半还得靠 P1-2；D13 只关掉了一半。**

## 八、代价（必须一起报，不能只报"做成了"）

| 项 | 实测 |
|---|---|
| 选择子流大小 | **40,903,590 字节 ≈ 41 MB**（k=3 × C=26 × 524,401） |
| 加密耗时 | 311 ~ 344 ms |
| ANSWER 耗时 | 50.9 ~ 52.9 s（明文列号基线 51.8 ~ 52.8 s）⇒ `load` 78 条密文的开销**落在机器抖动里**（单台机器两次运行之间单元标定就在 190~304 ms 之间变） |
| HTTP 请求体 | **96,199,421 字符 ≈ 91.7 MB**（基线形态 205 字符）⇒ 放大 **46.9 万倍** |
| 打包/解包 | 75 ms / 66 ms（5,843,370 个 long） |
| 服务器端处理 91.7 MB 请求 | 6.07 s（含 JSON 解析 + 78 条 load + 完整 ANSWER） |
| 进程内 `selftestSealed` 的出站 JSON | 96,202,922 字符（≈ 92 MB），只为做隐私断言也要先把它拼出来 |

**41 MB 是「`q^col_a` = C 条独立密文」这条读法的直接后果，不是本实现的浪费。**
对照：`q_BF` 只有 211 KB。这条读法记在 D3（它正是 `CtPtMul(ct,pt)` 能逐个相乘的原因），
但它的通信代价此前从未被量过 —— 现在量了。

**⇒ 如实结论**：如果 CAPE 真的按这条读法部署，列选择子会是**压倒性的通信瓶颈**，
比 `q_BF` 大 200 倍。这里只报数，不下"论文写错了"的结论 ——
那只可能是我们读法的问题，而**要判定它需要论文给出 query 的实际字节数**（论文没给）。

## 九、这一轮的教训（给下一次接手）

1. **断言给出绿灯，负对照给出真相。** 断言 1 一开始就是 PASS（因为两边都是 0）；
   是负对照 3 FAIL 才把底下的坏路径翻出来。**没有负对照的验收等于没有验收。**
2. **JNI 的数组类型要逐参数核对。** Java `int[]` ↔ C++ `jlongArray` 能编译、能链接、
   能跑，只是**静默算错**。核对清单里必须有一项"每个数组参数的 JNI 类型"。
3. **"返回成功但结果是 0" 的接口要当故障处理。** 501 闸门挡住了它伤到使用者，
   但根因是几个月后靠一次无关的负对照才挖出来的 —— 闸门不该替代根因定位。
4. **文档里的"未修完"要写清是"没实现"还是"实现了但坏了"。** 前者是进度，
   后者是 bug，两者的处理方式完全不同。

## 十、`tools/p1_repro.cpp` 与最初的崩溃（保留，因为它解释了 §3.1 的一个写法）

P1-1 的第一版在**第 2 次 `multiply_plain`** 上必崩
（`EXCEPTION_ACCESS_VIOLATION`，`memcpy(dest=NULL, len=524288)`）。根因是**变量作用域**：

```cpp
// ❌ 崩                                    // ✅ 能跑
Ciphertext accCol, prod;                    for (cc...) {
for (cc...) {                                   Ciphertext prod;   // 循环内
    multiply_plain(sel[cc], tab, prod);         multiply_plain(sel[cc], tab, prod);
    if (cc == 0) accCol = std::move(prod);      if (cc == 0) accCol = std::move(prod);
    else add_inplace(accCol, prod);             else add_inplace(accCol, prod);
}                                           }
```

`cc=0` 时 `prod` 是空的，正常分配；`std::move` 之后它内部的 `DynArray` 指针
**已被转移但未清空**；`cc=1` 再让它当输出 ⇒ `resize()` 去释放那个**已经属于 `accCol`
的指针** ⇒ 野指针释放。**修法一行：输出密文声明在循环内。**

现在的 `cape_answer_core` 就是这么写的，并且在函数头上把这条**写成注释**，
因为它的失败模式（第二次才崩）太容易让人往"参数/内存/加密内容"上猜。

> 当时立的规矩留着：**所有 native 侧的可疑操作序列，先在独立程序里验一遍。**
> `tools/run_seal_probe.ps1`（一条命令编译+运行）**秒级**一轮，
> 而 JNI 版每次要"重建 DLL(~40 s) + 起服务(~2 min) + 跑测试"，崩溃还会把 JVM 一起带走。
