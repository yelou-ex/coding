> ⇒ 建模 ANSWER 37.3 s → **29.7 s（2×）/ 27.1 s（3×）**。

## 二、量出来是什么

用**配对差分**（下面 §四 说明为什么不能用回归）：同一个 `B_pay`、同一个列，
只改列数 `C`，交替测 `C=1` 与 `C=26`，各取最小：

```
rep0: C=1 → 3893.6 ms ； C=26 → 4344.6 ms
rep1: C=1 → 3914.6 ms ； C=26 → 4310.5 ms
rep2: C=1 → 4081.6 ms ； C=26 → 4376.6 ms
rep3: C=1 → 3918.7 ms ； C=26 → 4277.6 ms
rep4: C=1 → 3874.0 ms ； C=26 → 4304.4 ms
取最小：C=1 → 3874.0 ms ； C=26 → 4277.6 ms

⇒ 每列边际成本 = 1.345 ms/单元
⇒ 列选择（C=26 次 multiply_plain）占一个单元的 9.8%
⇒ C: 1 → 26，单元 322.83 → 356.47 ms（+10.4%）
```

**两次独立测量一致**（另一组用 `-Dcape.prof.bpay=4`）：

| 测量 | 列选择占一个单元 |
|---|---|
| `B_pay=4` | **7.6%** |
| 默认 | **9.8%** |

> 为什么两次 `B_pay` 不同仍可比：列选择是**每 (路,块) 固定做 C 次**，
> 所以"每列每单元成本"与 `B_pay` 无关，占比也就与 `B_pay` 基本无关。
> 两者都在 **8–10%** 区间，互相印证。

## 三、⇒ 为什么说"模型的折数 ≈ 0"

NFLlib **只能**替换 `multiply_plain` 内部那一次**明文** NTT。而列选择本身
（`明文NTT + multiply_plain + add` 三项之和）只占一个单元的 **8–10%**，
那么：

| 假设 NFLlib 对这一行加速 | 列选择能省 | 单元能省（上限） | ANSWER（≈37 s）能省 |
|---|---|---|---|
| **∞（秒变 0，上界）** | 100% | **≤10%** | ≤3.7 s |
| 2× | 50% | ≤5% | ≤1.9 s |
| 3× | 67% | ≤6.7% | ≤2.5 s |

**⇒ 即使 NFLlib 把那一行加速到无限快，整个 ANSWER 也只能快约 10%。**
规划书那个"37.3 s → 29.7 s（2×）"的模型**不成立** —— 它隐含地把
"明文 NTT 占一次 CMUX 的 41.2%"当成了"占整个单元的可加速份额"。

### 3.1 那 41.2% 到底是什么（方向反了）

`CmuxBreakdown` 那个 41.2% 量的是**一次 CMUX 内部**的 NTT 成本。
而**盲旋转里的 NTT 是密文侧的**（`external_product` 的分解要
`transform_from_ntt`），NFLlib 替换的是**明文侧的 `multiply_plain`**。

> **⇒ 41.2% 那部分正是 NFLlib 加速不了的；NFLlib 能加速的那部分只占 8–10%。**
> 这不是"打几折"的问题，是**优化对象选错了**。

## 四、方法论：两次测量都错在"用回归量小信号"

**第一版**用"扫 `C` 做线性回归"。`B_pay=4` 那组给出了看起来合理的
`slope = 11.6 ms`，但**换 `B_pay=16` 直接给出负斜率** `−188 ms`：

```
T(C) = 14280.7 ms + C · (−188.4) ms     ← 物理上不可能
⇒ 列选择占一个单元 = −48.1%
```

原因：那个配置下单元总时长只有 ~200 ms，而**列选择那点信号
（几十毫秒）被机器状态抖动整个淹掉**。回归把噪声拟合成了负斜率。

**改成配对差分后信号稳定**（见 §二 的五个 rep 都在 ±5% 内）。三个要点：
1. 两个被测点用**同样多**的单元数（固定 `B_pay`，只改 `C`）；
2. **交替**测 `C=1` 与 `C=C`（A,B,A,B…），让机器漂移对两组同等作用、差分时抵消；
3. 各取**最小值**（= 干扰最少的那次）。

> **教训**：**要量的是小信号（占比几 %），就必须让两个被测点在时间上贴近、
> 且共享同一份机器状态。** 扫参数做回归在信号远小于抖动时会给出假斜率 ——
> 而且假斜率可能**看起来**很合理（第一版就没被自己发现，是换个 `B_pay` 才暴露的）。

## 五、这一轮**没有**解决的：单元的时间到底花在哪

本项只回答了"**不是**列选择"。但**单元的主体时间（~90%）在哪，现在没有答案** ——
这才是接着要量的问题。已知的候选：

| 候选 | 依据 | 状态 |
|---|---|---|
| 盲旋转里的 d 轮 CMUX（含密文 NTT + 分解） | `CmuxBreakdown` 量过，且 d 轮是主循环 | 最可能，**未逐项定量** |
| 表读取（`[C][B_pay][N]` 大表的内存带宽） | `measureUnitMs` 的注释已记过"读不到那张 135 MB 大表时单元小 1.4~2.0×" | **有旁证，未定量** |
| 每单元一次的解密 / 采样提取 | —— | 未量 |

**⇒ 如果还要做性能优化（P2），下一步应该是把单元按这三块拆开量**，
而不是继续换 NTT 库。换 NFLlib 即使成功，天花板也只有 ~10%。

## 六、对规划书 P2-1 的处置建议

| 项 | 建议 |
|---|---|
| 该不该继续等 NFLlib？ | **优先级大幅下调**：天花板 ~10%，而 NFLlib 的移植成本不低（API 大改、根表/对齐要核对） |
| 那 41.2% 还有用吗？ | 有用，但用途变了：它是**盲旋转内部**的成本，指向"**减少 CMUX 轮数**"这一类优化（例如 `levels`、分解方式），**不是**换 NTT 库 |
| `沙箱受限清单` 的 A1 | 可以**降级**（从"不拿到就没法继续"改为"低优先"）。第 4 节说它"只影响 P2-1"，现在 P2-1 本身的价值也变小了 |
