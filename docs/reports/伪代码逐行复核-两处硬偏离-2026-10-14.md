## 一、把"推断"升级为"原文"的四处

### 1.1 `Pack` 就是 `ct^{BF}_j` 的来源 ⇒ D2 与 Pack 是**同一个洞**（原文证据）

```
Alg 2 ANSWER 2: resp_anc ← FusePIR.Answer(st_S, q_anc)
Alg 2 ANSWER 3: Parse {(c_{v_j}, ct^{BF}_j)}_{j=1}^m from resp_anc
Alg 1 ANSWER 13: resp ← Pack({ct_{pay,b}}_{b=1}^{B_pay})
```

⇒ **候选的 Bloom 密文 `ct^{BF}_j` 是从 Pack 的输出里"解析"出来的。**
没有 Pack 就不存在 `ct^{BF}_j`。

规划书 §0.6.1 曾把「#2 没有 Pack」与「#3 候选 Bloom 密文不是检索出来的那条（D2）」
写成**收敛推断**（"它们是同一个东西的三个方面"）。现在它是**原文事实**：
D2 不是独立 bug，是 Pack 缺失的症状。

#### ⚠️ 连带更正：D2 的"真障碍"是**我们自己造的**

规划书此前写 D2 的障碍是：

> 真障碍 = `SampleExtract` 的 `q_R→Z_t` 缩放噪声（实测 |残差| ≈ 30 > 位值 1 的十几倍）

**Pack 是 ring packing（LWE→RLWE 打包 + 密钥切换），根本不做 `SampleExtract`。**
那堵墙是我们绕开 Pack、改用 `SampleExtract` 硬抠 Bloom 位才撞上的。

⇒ 口径应改为：**D2 不是"有真障碍所以先放着"，而是"没有 Pack，就只能走一条论文没走过的
笨路，而那条笨路有它自己的障碍"**。这条更正把 D2 的优先级**上调**（它不再是"难"，而是"缺件"）。

### 1.2 第 5 行把两把密钥写在同一行 ⇒ `s_L == s_R` 是**硬偏离**

```
Alg 1 SETUP 3: ... generate HE keys sk = (s_L, s_R).
Alg 1 QUERY 5: q_a = (q_a^col, q_a^row) = (RLWE.Enc_{s_R}(e_{c_a}), LWE.Enc_{s_L}(r_a)).
```

**同一行里，列选择子用 `s_R`、行选择子用 `s_L`。** 这无法再用"论文记法不严谨"解释 ——
两个下标是有意区分的。

⇒ P1-3 那条结论（我们的实现要求 `s_R == s_L` **逐位相等**，否则净旋转偏 5767 行）
现在是**对着原文的硬偏离**，而且 **P1-2（给 `q^row` 加噪声）也被它一并挡住**：
噪声要加在 `LWE.Enc_{s_L}(r_a)` 上，而我们的 `s_L` 不是独立的。

### 1.3 CAPE 的 `B_pay` 必须**重算**，而两个算法都没写 ⇒ 这是**我们的推断**

```
Alg 1 SETUP 6: y_{K_i} ← fp(K_i) || m_i || v_{i,1} || ··· || v_{i,m} ∈ Z_t^{B_pay}
Alg 2 SETUP 8/11: V^{CAPE}_{K_i} ← {(v_{i,j}, b_{v_{i,j}})}；整个交给 FusePIR.Setup
```

Alg 1 给的是 `B_pay = 2 + m`（每个值占 1 个 `Z_t` 元素）。CAPE 把每个值换成
`(v, b_v)`，于是每个值占 `1 + ℓ_BF` 个元素 —— **但 Alg 2 再也没提 `B_pay`**。

⇒ **CAPE 的 `B_pay = 2 + m(1 + ℓ_BF)`，我们的 59 = 2 + 3×19 正是这个式子，
但它是推断，必须显式标注为推断。**
它同时解释了为什么 Pack 在 CAPE 里比在 FusePIR 里重要得多：`B_pay` 从 5 变成 59。

### 1.4 `q^col_a[c]` 的读法：**C 条独立密文是唯一类型正确的读法**

```
Alg 1 QUERY 4: e_{c_a} ← (0,...,0,1,0,...,0) ∈ {0,1}^C
Alg 1 QUERY 5: q_a^col = RLWE.Enc_{s_R}(e_{c_a})          <- 单数、一个 C 维向量
Alg 1 ANSWER 5: Acc ← Σ_c CtPtMul(q_a^col[c], P_{c,b}(X)) <- 对 q^col 取下标 c，再当**密文**用
```

| 读法 | `q^col_a[c]` 是什么 | `CtPtMul` 是否类型成立 |
|---|---|---|
| (i) 一条密文装 one-hot 向量 | 向量的**分量** | ❌ 分量不是密文 |
| **(ii) C 条标量密文** | **第 c 条密文** | ✅ ct × pt |

⇒ **我们选 (ii) 不是偏好，是表达式类型逼出来的唯一读法**；
P1-1 实测的 **41 MB/查询**就是这条读法的价格。
（这一行伪代码本身写得不够严：若真是一条密文，应写成 `{RLWE.Enc(e_c)}_{c=1}^C`。）

## 三、🔴 新照出的两处硬偏离

### 3.1 默认路径的锚检索**写死读第 0 个关键词**（比在案缺口都严重）

**原文**：
```
Alg 2 QUERY 1:   (q_anc, st^C_anc) ← FusePIR.Query(pp_F, sk, K_1)
Alg 2 ANSWER 2:  resp_anc ← FusePIR.Answer(st_S, q_anc)
```

**我们**（`CapeDemoService:328`）：
```java
long[] payload = runAnchorNative();     // → runAnchorNative() 里是：
                                        //     cIdx[a] = tb.colOf[0];       ← 永远是"关键词 0"
                                        //     rIdx[a] = tb.rowOf[0] + a;
```

而客户端发的是什么（`CapeDefaultPathTest:180`）：
```
{"d": lBf, "qBFBytes": [...]}          白名单 = ["qBFBytes", "d"]
```

⇒ **客户端根本没发 `q_anc`，服务器也没读它。锚那一半查询在默认路径上不存在。**

三条连带后果：

1. **默认路径只能回答"锚 = DB 第 0 个关键词"的查询。** 别的锚会 `f = payload[0] =
   fp(关键词0) ≠ fp(K)` ⇒ 客户端返回 ⊥。
   **是响亮地失败，不是静默出错** —— 这要谢谢 P0-4 那条指纹校验。
2. **`selftestCape` / `CapeDefaultPathTest` 的绿灯，是"池子第 0 组恰好以关键词 0 为锚"换来的**，
   不是协议能力。这正是本仓库一直警惕的"绿灯但没证明什么"。
3. **"出站白名单只有 `[qBFBytes, d]`"这条被当成隐私成果的证据，
   同时就是协议少一半的原因。**

> 附一条口径瑕疵：那个 `d` 字段填的是 `lBf`（18），而 `CapeQuery.toJson` 里的 `d`
> 是 **LWE 维数**（16）—— **同一个字段名在两个请求里指两个量**，而且服务器根本不读它。

### 3.2 `ctPay` 是明文，而且里面就装着候选值 id

**原文**：
```
Alg 1 DECODE 2-4: y[β] ← Dec_{s_R}(ct_{pay,β})        <- **客户端**解密
Alg 2 ANSWER 8:   resp ← ({(c_{v_j}, ct_{score,j})})   <- 返回的是**加密的**候选值
§4.1: "Only the **encrypted** candidate values and these scores are returned to the client."
```

**我们**（`CapeDemoService:368`）：
```java
long[] payload = runAnchorNative();   // runAnchorNative 返回的是 nativeCapeAnswer 的**解密结果**
out.put("ctPay", payload);            // ← 字段名声称是密文，值是明文
```
而载荷布局是 `[0]=指纹, [1]=候选数, 之后每候选 1+ℓ_BF 项（第 1 项就是 value id）`。

⇒ **上一轮"响应里不再发明文 `valueId`"这个修复，在回环里是<u>名义上的</u>**：
同样的 id 仍在同一份响应里，只是从独立字段搬进了载荷数组，还被命名为一个"密文"。

**这正是本仓库已经吃过一次的坑**：`bf` 改名成 `d2PlaintextBf` 就绕过了按名字查的断言
（见 `CapeSealedFlowTest` 1 节的注释与缺陷总表）。**同一个模式又发生了一次，只是方向相反**
（上次是把明文藏在一个无害的名字后面，这次是把明文挂上一个"密文"的名字）。

**为什么它的真修要等 Pack**：要让服务端不解密，就得把 `sumCt[b]`（B_pay 条密文）
发出去 —— 按实测单条 **524,401 字节**推算，`59 × 524,401 = 30,939,659 字节 ≈ 30.9 MB/响应`
（**这是推算，不是实测**）。而 Pack 存在的意义正是把这 59 条压成几条。
⇒ **先改这一处等于白改**：Pack 一做，这里本来就要重写。

## 五、修复（本轮执行）

| # | 项 | 做法 | 验收 |
|---|---|---|---|
| ① | 默认路径锚检索写死 | `/api/query` 收 `anchorColIdx`/`anchorRowIdx`，走客户端给的锚；**缺了就报错**，只有 `-Dcape.fixedAnchor=true` 才允许回退且响应显式标注 `anchor` | **新增"锚 ≠ 关键词 0"用例**（修复前必失败）+ 白名单更新 |

| ③ | D2 的"真障碍"归因 | 文档更正（§1.1） | 本报告 |

> ①的修复方式说明：`colIdx`/`rowIdx` 由**公开哈希 H** 算出，所以任何客户端都能算；
> 而 `β` 需要与累加器同一把秘密（回环限制），所以这里走的是
> `nativeCapeAnswer`（服务器自造 LWE 索引）这条**基线形态**。
> 也就是说：**修 ① 只关掉"写死关键词 0"，不关掉 D3/N5 的 `(c_a, r_a)` 可还原** —— 那是 P1-1/P1-2 的事。
