## 一、先纠正一条可能的误解：**我们现在的列选择并不违反 CAPE**

我一开始怀疑"客户端送 C 个 one-hot 密文"是错的。**查原文后否掉了这个怀疑：**

| 论文原文 | 位置 | 含义 |
|---|---|---|
| `Algorithm 2 CAPE` … `1: (q_anc, st_C) ← FusePIR.Query(pp_F, sk, K_1)` | `out_cape.txt:985-989` | CAPE 的锚检索**直接委托给 FusePIR** |
| "The client generates encrypted **row and column selectors** for the three BFF positions" | `:740-741` | FusePIR 基准版就是 one-hot selector |
| "Inspired by PirouetteH, **FusePIR-C replaces the large RLWE one-hot selector with compact LWE encryptions of its coordinates** and expands the selector homomorphically at the server. **CAPE-C inherits the same optimization**" | `:243-249` | **只有 C 变体**才做选择子压缩+扩展 |
| `13: Acc_{a,b} ← Σ CtPtMul(q̂_col[c], P_{c,b}(X))`（带帽） | `:2138` | 这行属于 **Algorithm 5 CAPE-C**（`:2057` 起），不是 Algorithm 2 |

我们 `sq.qCol[a][c] = Enc(c == c_a ? 1 : 0)` ⇒ **正是基准版 FusePIR/CAPE 的 one-hot RLWE selector**。

**⇒ 两篇新论文对应的是 `CAPE-C` / `Appendix B` / `Algorithm 5` —— 一个我们此前明确判定"不做"的变体。**
所以下面的"缺点"性质是：**我们没做那个变体**，而不是**我们把基准版做错了**。

## 二、真正的缺点（4 条）

### 缺点 1｜上传通信量是 C 倍，客户端还多做 C−1 次加密
- 现状：`k × C` 个密文。k=3、C=4 ⇒ **12 个**。
  N=4096、2 个工作素数时每个约 131 KB ⇒ 上传约 **1.5 MB**。
- 变体：`k` 个紧凑密文 ⇒ **3 个**、约 393 KB。
- 客户端：12 次 `m.encrypt`（每次含 NTT + 噪声采样）⇒ 3 次。
- 论文原话就是这个 trade-off："trading **additional server computation** for **substantially
  smaller upload communication**"（`:247-249`）。
- ⚠️ 诚实标注：**C=4 时收益很小**（12→3）。C 是数据库列数，论文规模下才显著。

### 缺点 2｜★ 参数与 SealPIR 的噪声优化**不兼容** —— 最实质的一条，但**已被 4.1④ 绕开**
SealPIR 给出的扩展噪声界（Theorem 2，`out_sealpir.txt:1745-1762`）：

```
v_out ≤ t · ( 2^⌈log n⌉ · (v_in + 2·B_sub) )          n = 扩展出的条目数
      ≈ t · n · v_in
```

那个 **`t` 因子来自最后一步**：为了把 `Enc(2)` 变成 `Enc(1)`，必须乘 `α = m^{-1} mod t`
（`m = 2^⌈log n⌉`）。**乘一个模 t 的常数 ⇒ 噪声乘 t。**

SealPIR §6 专门为此给了个优化（`:1117-1131`）：把明文模数从 `t = 2^y` 换成
`t' = 2^{y−⌈log n⌉}`，就可以**免掉这次乘法与求逆，并降低扩展噪声**。
原文明确写：**"This optimization requires `t` to be divisible by `m` rather than being an odd integer."**

**我们的参数直接卡死这条路：**
- 我们 `t = 65537`（素数）。
- 为了 SIMD 槽编码必须 `t ≡ 1 (mod 2N)`（65537 mod 8192 = 1 ✓）。
- 素数 `65537` **永远不可能被 `m = 2^⌈log n⌉` 整除** ⇒ **SealPIR 的噪声优化用不了**。

⇒ 只能吃满 `t · 2^⌈log n⌉`：C=4 时 = `65537 × 4 ≈ 2.6×10^5` 倍的输入噪声放大。

**而我们已经实测过噪声的敏感度**（`SampleToPackLink`）：残留噪声 `std ≈ 15`、峰值 28
就已经让 `s_j == τ` 这种精确判等失效。**⇒ 直接照搬 EXPAND 大概率解密失败。**

### 缺点 3｜k 路之间没有共享结构（这条**不能顺手修**）
OnionPIR 的 `QueryPack`（Alg.1，`:581-602`）把**所有维度的查询向量打包进单个明文再加密**
（`:606-612` 原文："All the query vectors are packed into a single plaintext pt, which is then
encrypted using BFV. … **a single plaintext is sufficient to pack all the query vectors**"）。

对我们就是 `k × C → 1` 个密文的潜力。**但** OnionPIR 的解包（Alg.2，`:642-672`）需要
`A = RGSW(−s)` 并"perform external products between the RGSW encryption of the client
secret-key and the bottom `l` rows"（`:620-622`）—— 即 **`LWEtoRGSW`**，
正是我们标为 ⏸ 离关键路径的那个原语。⇒ **要接 QueryPack 必须先做 `LWEtoRGSW`。**

### 缺点 4｜客户端把"选择"做在明文侧，丢掉了稀疏性杠杆
- SealPIR 送的是**单项式** `Enc(x^i)`（`:416-419`），只有 **1 个非零系数**；
  扩展里 `c_1 = c_0 · x^{−2^j}` 是"乘单项式"，而 Thm 2 的证明明确
  **"Plain multiplication by a monomial x^j with coefficient 1 does not change the noise"**（`:1740-1741`）。
- 原文还说扩展成本"is based on the number of non-zero coefficients"（`:304`）。
- 我们送的是 C 个**独立的完整密文**，每个都带满系数的新鲜噪声 —— 没有稀疏性红利。

## 三、能修缮吗 —— 分三档

### A 档｜只做选择子扩展（小、可做、收益小）★ API 已验证可行
把 `k` 路的列选择子从"C 个独立密文"改成"**1 个单项式 `Enc(x^{c_a})` + 服务端 EXPAND**"。

**语义上是严格 drop-in 的**：SealPIR 扩展出的 `o_j` 加密的是**常数多项式 1**，
当 `j = c_a` 时 `o_j ⊛ P_{c,b}(X) = Enc(P_{c_a,b}(X))` ——
**和我们现在的 `Enc(1_{c=c_a})` 逐字等价**。我们的 C 个密文，就是 EXPAND 的输出被客户端
在明文里算好了而已。

**API 可行性已核对**（`javap` 本仓库 `lib/mpc4j-crypto-fhe-seal.jar`）：
```
KeyGenerator.createGaloisKeys(int[] galoisElts, GaloisKeys)      ✅ 存在（不是只有 step 版）
Evaluator.applyGalois(Ciphertext, int galoisElt, GaloisKeys, Ciphertext) ✅ 存在
```
⇒ SealPIR 的 `Sub(c, k)`（`x → x^k`）**能实现**，不必新造原语。
对 N=4096、C=4：Galois 元素是 `N/2^{j+1}+1` = **2049、1025**（皆奇数、皆 < 2N=8192 ✓）。

**服务端代价可忽略**：C=4 只需 2 层、约 6 次 `applyGalois` + 几次明文乘。
按我们实测的盲旋转 15.6 ms/CMUX 量级，这最多是 **~0.1 s**，而 ANSWER 是 50 s。

**⇒ A 档唯一的不确定性就是缺点 2 的噪声。** 必须先实测。

### B 档｜A + 复现 SealPIR §6 的噪声优化（中）
需要把扩展用的明文模数换成 `t' = t / 2^⌈log n⌉`。
**代价**：SealPIR 原文自己指出 "the server must represent the database using FV plaintexts
defined with the plaintext modulus t′ … **we can pack fewer database elements into a single
FV plaintext**"（`:1128-1131`）。我们这边 `t=65537` 还要服务 SIMD 槽，**与槽编码冲突**，
需要单独评估要不要给"选择子/数据库"分两套模数。

### C 档｜完整 CAPE-C（大）
Appendix B / Algorithm 5：`LWEtoRGSW` + selector expansion + `QueryPack`。
这是我们之前判定**不做**的范围；缺点 3 必须落在这里。

## 四、判别实验已执行：`ExpandProbe` —— **结论是「能修缮」，16 PASS / 0 FAIL**

实现：`coding/rgsw-lab/src/main/java/com/fusepir/rgsw/ExpandProbe.java`
复现：`.\run-mpc4j.ps1 -Class com.fusepir.probe.ExpandProbe 4096 4`

### 4.1 四条实测结论

**① Galois 替换 `Sub(c,k)` 在我们这条路线（MPC4J 纯 Java SEAL）上可用。**
`javap` 核对 + 实跑确认：
```
KeyGenerator.createGaloisKeys(int[] galoisElts, GaloisKeys)              ✅
Evaluator.applyGalois(Ciphertext, int galoisElt, GaloisKeys, Ciphertext) ✅
```
⇒ **不需要新造原语**，也没有撞 `step count too large`。

**② 论文 Figure 3 印的 Galois 指数整体差一层。**
两处指数在原文里就不一致（正文 n=2 用 `Sub(c, N+1)`，Figure 3 用 `N/2^{j+1}+1`）。
按群论推导：第 j 层要满足 `d·(e_j−1) ≡ N (mod 2N)`，得 **`e_j = N/2^j + 1`**
（N=4096、C=4 时为 **4097、2049**）。
实测裁决（A 段，把错的当负对照）：
| e | i=0 结果 | i=1 结果 | 判定 |
|---|---|---|---|
| **4097** (= N+1，j=0) | `o_0=2`、余项**全零**；`o_1=0` | `o_0=0`；`o_1=2`、余项**全零** | ✅ 干净 one-hot |
| 2049 (= N/2+1，若当 j=0)
| `o_0=2` **但 `o_1` 余项非零** | `o_0` 余项非零 | ❌ 不是 one-hot |

⇒ **指数取 `N/2^j + 1`**；直接抄 Figure 3 的 `N/2^{j+1}+1` 会得到"第 0 项看着对、高阶项全错"的假成功。

**③ 扩展本身正确，代价是 8 bit 噪声换 C 倍通信。**
| 量 | 值（N=4096, t=65537, C=4） |
|---|---|
| 新密文噪声预算 | 51 bit |
| 扩展后（不乘 α） | 45~46 bit |
| 再乘 α 后 | 31~32 bit（**掉 15 bit ≈ log₂t**，正是 Theorem 2 的 t 因子） |
| 列选择后（现有做法 = C 个独立新密文） | 38 bit |
| 列选择后（扩展做法 = 一次扩展） | 30 bit（**多花 8 bit**） |
| 上传通信量 | **4 个密文 → 1 个**；客户端加密 **4 次 → 1 次** |

**④ ★ `α` 那一步可以整个不做 —— 这是本项目的改进，SealPIR 自己没有。**
EXPAND 的输出不是终点，它要喂给 `CtPtMul(o_c, P_c)`。把 α **在明文侧折进表**
（`P'_c = C^{−1}·P_c mod t`，建库时即可算完）：
```
Σ_c CtPtMul(C·1_{c=sel}, C^{−1}·P_c) = Σ_c (C·C^{−1})·1_{c=sel}·P_c = P_sel
```
**密文侧一次 α 乘法都没有** ⇒ Theorem 2 里那个 `log₂t ≈ 16 bit` 的因子**消失**。
实测（D 段）四个列的还原值**精确等于** P：
`[1000,1001,1002,1003]` / `[1137,…]` / `[1274,…]` / `[1411,…]`。
SealPIR 做不到这点 —— 它扩展出的向量要被当作答案直接返回、或继续做 ct×ct，
所以必须实打实乘一次 `m^{−1}`。

⇒ **所以缺点 2 那条"参数不兼容"的死结被绕开了**：既不用改明文模数、不破坏 SIMD 槽编码，
也不用吃 `t` 因子。**B 档（换明文模数）不再需要。**

### 4.2 值得记的踩坑（已写进类注释）

第一版把 `α` 写死成 `2^{−1} mod t`，C=4 时**所有**读数都呈现"乘了 α 但结果没变"，
看上去像 MPC4J 的 bug（我先按"Galois 降层后 `multiplyPlain` 不可信"记了一轮）。
打印原始读数才看到选中项解密是 **`c0=4`** —— SealPIR 的循环不变量是
**结束时选中项加密的是 `m = 2^ℓ = C`**，所以 **`α` 必须是 `C^{−1} mod t`**（不是 `2^{−1}`）。
写死 `2^{−1}` 时 `C·(2^{−1})·P = 2P`，B/D 两段的偏差**全部**由此解释。

> **教训**：这类"看起来像库有问题"的现象，先核对循环不变量，再怀疑库。

### 4.3 结论：A 档可以做了

| 档 | 状态 |
|---|---|
| **A 档**（单密文 + 服务端 EXPAND） | ✅ **已验证可行**，且噪声代价只有 8 bit。指数、Galois API、α 折表三件事都已落实 |
| **B 档**（换明文模数做 SealPIR §6 优化） | ✅ **不再需要**（4.1④ 已经免掉 α 乘法） |
| **C 档**（完整 CAPE-C，含 `LWEtoRGSW`） | 仍未做；缺点 3 落在这里 |
| **缺点 3**（k 路共享 / QueryPack） | ❌ 未解决，且**必须**先有 `LWEtoRGSW` |

**剩下一件事是把 A 档接到 `CapeEndToEnd4` 的 QUERY/ANSWER 上**（12 个密文 → 3 个）；
本实验只验证了原语层，没动主链路。
