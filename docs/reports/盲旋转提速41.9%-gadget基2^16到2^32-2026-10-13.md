## 2. 为什么这是可行的

### 2.1 成本公式里唯一的自由变量

一次 CMUX = 一次 external product =

```
2 × levels × [ transform_from_ntt + CRT 重组 + 分解 + transform_to_ntt + multiply_plain ]
```

而（`rgsw_blindrotate.cpp` 第 510–523 行）：

```
levels = min l : base^l > q
```

**所以 base 翻倍 ⇒ levels 减半 ⇒ CMUX 的五步全部减半。** 这是能线性砍掉 98% 的唯一旋钮。

### 2.2 真正的约束是 `t`，不是安全参数

平衡分解取 `r = x mod base`，若 `r > base/2` 就进位、该位存 `r − base`（负数存成 `t + r`）。
而 `r` 是**明文系数**，必须落在 `[0, t)`：

```
base/2 < t   ⇒   base < 2t
```

现网 `t = 65537` ⇒ **`base` 最大只能是 2¹⁶**。这就是「基锁死在 2¹⁶」的真正原因 ——
**是明文位宽顶住的，不是 q，也不是安全级别。**

把 `t` 抬到 2³² 后，`base` 就能一路抬到 2³²。实测：

| t | b | levels | qBits | 1 次旋转 | ms/CMUX | 相对 | 盲旋转后噪声 | 正确性 |
|---|---|---|---|---|---|---|---|---|
| 65537 | 16 | 11 | 174 | 276.9 | 25.17 | 基线 | **128 bit** | PASS |
| 65537 | ≥20 | — | — | — | — | — | — | **FAIL**（位 > t−1） |
| 2³² | 16 | 11 | 174 | 454.8 | 41.34 | +64% | 112 bit | PASS |
| 2³² | 20 | 9 | 174 | 316.9 | 35.21 | +14% | 108 bit | PASS |
| 2³² | 24 | 8 | 174 | 247.5 | 30.94 | −11% | 105 bit | PASS |
| 2³² | 28 | 7 | 174 | 195.0 | 27.85 | −30% | 101 bit | PASS |
| **2³²** | **32** | **6** | 174 | **156.4** | **26.07** | **−44%** | **97 bit** | PASS |
| 2³² | 36 | — | — | — | — | — | — | FAIL（位 > t−1） |

### 2.3 噪声撑得住

| 阶段 | t=65537, b=16 | t=2³², b=32 |
|---|---|---|
| 1 轮 CMUX 之后 | 153 bit | 137 bit |
| **整条盲旋转之后** | **130 bit** | **97 bit** |

t 从 16 bit 涨到 32 bit，噪声只多吃了 **33 bit**（130→97），而速度拿到 −36.5%。
**代价与收益完全不成比例地划算。**

> 为什么抬 t 只吃 33 bit：BFV 里 `t` 变大主要影响「标量编码的分辨率」，
> 而这里每个槽只放一个远小于 t 的系数；噪声项里 `t·e` 那一份涨了 16 bit，
> 再加上分解误差从 `2¹⁵` 涨到 `2³¹`（+16 bit）≈ 合计 ~33 bit。

## 3. 顺带查出并修掉的两个真 bug

### 3.1 `decomposeValueMw` 里 base 是**失效参数**（已修）

```c
// 改前：digit 用 base 取，位移却硬编码 16
const uint64_t r = x[0] & (c->base - 1);
mwShiftRight16(x, W);          // ← 永远移 16 位
```

`levels` 又是按**传入的 base** 算的 `⌈qBits/baseBits⌉`。于是只要 `base ≠ 2¹⁶`，
「取位宽」和「移位宽」就对不上：`levels` 轮之后余项还剩 `~q/2^levels` 而不是 0，
**重建是错的，而且不报错**（`base=2¹⁶` 时两者恰好一致，所以一直看不出来）。

**修法**：新增 `mwShiftRightBits(x, W, bits)`，按 `c->base_bits` 移。
修完 base=2¹⁶、≥20 两档行为完全不变（原路径 `4 PASS / 0 FAIL`，噪声 153/128 bit 逐位相同），
而 ≥20 现在是**明确报错**而不是静默算错。

### 3.2 `rnd.nextInt((int) t)` 在 t ≥ 2³¹ 时溢出崩溃（已修）

`CapeDemoData.java` 第 231 / 245 行把 `t` 强转 `int`。t=2³² 时强转成 0，
`Random.nextInt(0)` 抛 `bound must be positive`。改用 `rnd.nextLong(bound)`。
`t = 65537` 时两者等价。

### 3.3 一条必须记住的耦合约束

`build_rgsw_constant` 只建 `levels` 个密钥，而 `blind_rotate` 按 `d` 轮索引 `bk[i]`
⇒ **必须 `d ≥ levels`，否则越界读**。现网写死 `d=16` 与 `levels=11` 是巧合安全；
base 一改 `d` 就必须跟着改。`blind_rotate` 内部 `a[i] % 2N == 0` 会 `continue`
（跳过恒等轮），所以 `d > levels` 不会算错，但**白跑**。

## 4. 怎么落地

改动只在**探针层**（生产链路不用动，因为 `t`/`base` 本来是硬编码在同一处）：

| 文件 | 改动 |
|---|---|
| `rgsw_blindrotate.cpp` | `mwShiftRight16` → `mwShiftRightBits(x,W,c->base_bits)`（**真 bug 修复，与提速路线无关也该修**） |
| `CapeDemoData.java` | `nextInt((int) t)` → `nextLong(t)`（**真 bug 修复**） |
| `CapeDemoService.java` | `T` / `BASE_BITS` 改为可覆盖：`-Dcape.t=4294967296 -Dcape.b=32` |
| `CapeAnswerSplit.java` | `t`/`base` 可覆盖；`d` 由 `levels` 推出而不是写死 16；加端到端 payload 校验 |
| `RgswBaseSweep.java` | 新增：base × t 扫描 + 噪声余量报告 |

复现：

```powershell

.\run-mpc4j.ps1 -Class com.fusepir.probe.CapeAnswerSplit 8192 .../keywords.json
```

> ⚠️ **默认没有改**。`-Dcape.t` / `-Dcape.b` 不传时行为与改前完全一致（t=65537, base=2¹⁶）。

## 5. 代价与**不要夸大**的地方

| 项 | 说明 |
|---|---|
| **每层变贵** | `t=2³²` 让 `multiply_plain` 从 0.54 ms 涨到约 0.84 ms（明文模数 >2³¹ 后 SEAL 的 multiply-and-round 基数变大）。所以是「**层数减半 > 每层涨价**」才净赚 |
| **列选择占比升到 3.2%** | 因为它按 `C×B_pay` 线性，不随 levels 变。配合 `R=64` 可回到 0.9%（实测 93 605 ms） |
| **无安全性主张** | 本演示本来就是玩具参数（`ε_BF=2⁻⁶`，`B_pay=83` vs 论文 665 092）。t=2³² 后更弱 —— **必须和原有免责声明一起讲，不能说「安全」** |
| **`t` 的下界没推导** | 实测 2³² 能用、噪声余 97 bit。真正能降到多少（2³²? 2⁴⁰?）**没测**，因为 `base` 受无符号 64 位限制也到 2³² 为止 |
| **论文可比性** | 论文 `t=65537`、`N=16384`。改成 `t=2³²` 后**参数集与论文不再一致**，别再拿 Table 3 直接对比 |

## 6. 更新后的成本账

```
ANSWER = k × B_pay × [ C × 0.54 ms  +  d × ms/CMUX ]

改前：249 × [ 26 × 0.54  +  11 × 41.38 ]  ≈ 160 s 盲旋转 + 3.4 s 列选择   → 实测 176 s
改后：249 × [ 26 × 0.54  +   6 × 26.28 ]  ≈ 105 s 盲旋转 + 3.5 s 列选择   → 实测 102 s
```

**下一步还能动的（按收益排序）：**

1. **`maxSetSize` → 2**：单元数 249 → 约 177（`B_pay` 83→59），再 −29%。
2. **`decompose` 的多字 CRT 往返**（下一个最大的一块）：
   一个 external product 要做 `2 × levels` 次分解；
   `decompose()` 里每个系数都要走一遍**多字 Garner 重组 + 多字分解**
   （`crtComposeMw` 里 `levels` 层 `mwModWord`/`mwAddMulWord`/`mwMulWord`），
   白盒剖面量过 **0.30 µs/系数**。它的成本**与 `levels` 无关**（每系数一次，
   内部固定 11 次移位），所以 `levels` 11→6 之后它在 CMUX 里的**占比反而翻倍**：
   按 0.30 µs × 8192 × 2 ≈ **4.9 ms**，对新的 26.28 ms/CMUX 是 **约 19%**
   （改前对 41.38 ms 是约 12%）。
   OnionPIRv2 的 `decompose_rlwe_single_mod` 走「逐素数有符号位提取 + 复用 scratch」，
   可以避开多字往返 ⇒ 这是**下一个值得测的方向**。
3. **`R = 64`**：列选择 3.5 s → 0.85 s（1.6%），顺手。
