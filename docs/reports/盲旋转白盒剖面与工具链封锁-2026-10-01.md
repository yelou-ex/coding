## 2. 整机基线（可靠）

`BlindRotateBench` 隔离纯 native 盲旋转（`nativePrepare`/`nativeRunWithCtx`，
不经 Java 表构建与 JNI 大数组搬运）：

| d | ms/rotate | **ms/CMUX** |
|---|---|---|
| 1 | 21.168 | 20.675 |
| 4 | 81.589 | 20.483 |
| 16 | 316.554 | **19.872** |

离散度 **4.0%** ⇒ 成本由 CMUX 主导、与 `d` 无关。
⇒ **每次 CMUX ≈ 19.9 ~ 20.7 ms**（这是最可信的一个数）。

交叉验证：330 单元 × 16 轮 × 20 ms ≈ **106 s**，占 ANSWER 147 s 的 **72%**。

## 3. 白盒剖面（独立 C++，直接调 SEAL）

`cmux_profile.cpp`，N=8192 / 4 素数 / **levels=11** / t=65537，基线 SEAL：

| 组件 | 实测 | 备注 |
|---|---|---|
| `transform_to_ntt`（一组多项式） | **0.72 ~ 0.79 ms** | 经 `Evaluator`，含目标拷贝 |
| `multiply_plain`（密文 × 明文） | **0.147 ~ 0.159 ms** | |
| 构造单项式明文 + NTT | **0.244 ~ 0.276 ms** | ← `multiply_power_of_x` 每次都要付 |
| RGSW 密钥构建（2×levels=22 次 `encrypt_symmetric`） | 38 ~ 47 ms | 与整机 16 键 ≈ 900 ms 量级一致 |

### 3.1 ⚠️ 一个我曾误判的"矛盾"，已查清 —— **错在我**

第一版剖面测出一次 `external_product` = 16.4 ~ 28.5 ms，我当时写：

> 2 × external_product (33 ms) > 整个 CMUX (19.9 ms)，矛盾。

**这个"矛盾"是我算错了，不是测量错。** 我记错了 `cmux()` 的结构。
看一眼源码 `rgsw_blindrotate.cpp:374-380`：

```cpp
// CMUX(bk, a, b) = a + (b - a) * bk
void cmux(...) {
    c->evaluator->sub(b, a, diff);
    external_product(c, bk, diff, prod);      // <-- 只调一次
    c->evaluator->add(a, prod, out);
}
```

**`external_product` 每次 CMUX 只调用一次，不是两次。** 所以根本没有矛盾：
一次 external_product ≈ 20 ms ⇔ 一次 CMUX ≈ 19.9 ms，**完全自洽**。

这个错误的教训记在这里：我当时是从"CMUX 应该在 a 和 b 之间做两次选择"这个
**记忆**去推的，而不是去读那 5 行源码。事后用 `decompose_cost.cpp` 独立复现
external_product ≈ 16.8~19.2 ms，与整机 CMUX 一致，才把这件事钉死。

## 3.2 ✅ decompose 到底占多少（这是本轮真正的答案）

`decompose_cost.cpp`：把 `rgsw_blindrotate.cpp` 里的多字算术**逐行照搬**成独立程序
（含每次调用的 vector 分配与系数域拷贝这两个开销），在**真实密文**上计时：

| 组件 | 实测（3 次重复） | 占比 |
|---|---|---|
| **`decompose`（两个分量，即一次外积所需）** | **4.61 / 4.86 / 4.96 ms** | **≈ 24%** |
| **库操作（22 次"准备+NTT" + 22 次 multiply_plain）** | **16.84 / 17.32 / 19.16 ms** | **≈ 76%** |
| 合计（独立复现的 external_product） | ≈ 21.7 ms | 对照整机 CMUX 19.9~20.7 ms ✓ |
| 整机实测一次 CMUX | 19.9 ~ 20.7 ms | — |

**⇒ 结论：`decompose` 只占约 24%，库操作占约 76%。**

这直接回答了第 6 节原本的疑问，答案是 **(A)**：库操作解释了大部分时间，
`decompose` 不是主战场。

### 3.3 但 decompose 内部已无明显浪费

`decompose` 处理 2 × N = 16384 个系数，耗时 4.9 ms ⇒ **0.30 µs / 系数**。
每个系数要做 4 素数 Garner 合成（含 3 次 `mwModWord`、每次最多 4 轮 128 位除法）
+ 11 个平衡数字抽取。**0.30 µs/系数已经很紧**，而它只占 24%。
⇒ 即使把 `decompose` 优化到零，CMUX 也只从 20.3 ms 降到约 15.4 ms（**-24%**），
而且是几乎不可能达到的上限。


## 4. 从可靠数字能推出的东西

用**可靠**的三个数（NTT 0.77 ms、`multiply_plain` 0.15 ms、单项式构造+NTT 0.27 ms）：

- 一次 `multiply_power_of_x` 的**大部分成本不是乘法**，而是
  "构造单项式明文 + 给它做 NTT"（0.27 ms vs 0.15 ms）—— 即**超过一半**花在准备输入上。
- 一次 `external_product` 需要 `2×levels = 22` 个明文，每个都要
  "填数组 + NTT"：纯准备 ≈ 22 × 0.27 = **5.9 ms**，纯乘法 ≈ 22 × 0.15 = **3.3 ms**。
  ⇒ 准备比乘法贵 **1.8 倍**。
- 盲旋转每次调用 `multiply_power_of_x` 共 `d+1 = 17` 次 ⇒ 17 × 0.27 ≈ **4.6 ms**
  是纯准备开销。×330 单元 ≈ **1.5 s**。

### 4.1 一个可做但收益小的具体优化

`multiply_power_of_x` 每次重建同一个单项式并重做 NTT。
它的入参 `a[i]` 在整个 ANSWER 里是**固定的**（`av[3][16]` 在单元循环外只生成一次），
所以这些 NTT 化单项式**完全可以缓存**。

预估：省掉 17 × 0.27 ≈ 4.6 ms/单元（占 CMUX 的 23%？不，这是**按单元**不是按 CMUX）——
按单元算是 4.6 ms，占单元 316 ms 的 **1.5%**。
⇒ **收益约 1.5%，太小，不值得动。**

（这里我把先前"值 0.8%"的估算更新为 1.5%，依据是本次实测的 0.27 ms 单项式成本
与每单元 17 次调用。）

## 5. 成本账（已闭合）

一次 CMUX（源码 `rgsw_blindrotate.cpp:374-380`）= `sub` + **1×external_product** + `add`：

| 项 | 实测 | 占 CMUX |
|---|---|---|
| `decompose`（2 分量） | 4.9 ms | **24%** |
| 库操作：22×（填明文 + NTT）+ 22×multiply_plain | 16.8 ms | **76%** |
| `sub` + `add` | 余量 | 小 |
| **合计** | **≈ 19.9 ~ 21.7 ms** | 与整机实测一致 ✓ |

### 5.1 库操作内部还能拆（用第 3 节的可靠单件成本）

22 个明文 × (0.27 ms 构造+NTT + 0.15 ms multiply_plain) ≈ 9.3 ms。
实测 16.8 ms ⇒ **还差约 7.5 ms** 在 22 次 out-of-place `multiply_plain` 的
输出分配、拷贝与 add 上。这部分属于 SEAL 内部行为，我们改不动。

### 5.2 唯一还看得见的"算法级"杠杆：减小 levels

`levels = ceil(qBits / 16) = 11` 直接决定外积要做 2×11 = 22 次明文乘法。

| gadget base | levels | 2×levels | 外积明文乘法次数 |
|---|---|---|---|
| 2¹⁶（现在） | 11 | 22 | 22 |
| 2³² | 6 | 12 | **12（-45%）** |

**但这条路被噪声卡死了，不是一个可选参数。** 依据是 `Mpc4jRgsw.decomposeFast`
里那条已验证的约束：

> 平衡数字窗口是 `±(t−1)/2 = ±32768`，而 `base = 65536 = 2¹⁶` **正好顶在窗口上**。

窗口 = ±2¹⁵ 且 base = 2¹⁶，说明**平衡数字的表示范围恰好被 base 用满**。
取 base = 2³² 需要窗口 ±2³¹，而窗口上限由 `t` 定死（`t = 65537`）⇒ 直接溢出。
要放大 base 就必须同时放大 `t`，`t` 一放大明文槽位跟着变、噪声预算也会吃紧
（我们在 N=4096 上只有约 51 bit 余量）。

⇒ **不是"调个参数就快 45%"，而是"要重新论证整套参数"。** 这是本研究之外的工作量。


## 6. 下一步建议（按性价比，已按本轮的实测重排）

先把结论摆明：**`decompose` 不是主战场**（24%），**库操作占 76%**。所以——

| # | 动作 | 预估收益 | 成本/风险 |
|---|---|---|---|
| 1 | **换 MSVC 工具链 + Intel HEXL** | **唯一能同时加速"22 次 NTT + 22 次 multiply_plain"的办法**（那正是 76% 那部分） | 很高：本机没有 MSVC，要先装整套工具链 |
| 2 | 减少 `levels`（改 gadget base / `t`） | 理论上可 -45% 明乘法，但**被噪声窗口卡死**（见 5.2） | 极高：要重新论证整套参数 |
| 3 | 减少 CMUX 次数（算法层） | 线性收益（已由"与 d 无关"证明） | 高：要动旋转结构 |
| 4 | 优化 `decompose` | **上限仅 -24%**，且它已是 0.30 µs/系数 | 高：伤筋动骨，收益有限 |
| 5 | 缓存 NTT 化单项式 | **≈1.5%** | 低，但不值得做 |

**判断**：本机唯一有实质希望的是 **#1（MSVC+HEXL）**，因为 76% 的时间花在 SEAL 的
`transform_to_ntt` / `multiply_plain` 上，而这两个正是 HEXL 加速的目标。
在此之前，**#4 和 #5 都不值得动手**（一个上限 24% 且已很紧，一个只有 1.5%）。
