## 2. 整机基线（可靠）

`BlindRotateBench` 隔离纯 native 盲旋转（`nativePrepare`/`nativeRunWithCtx`，
不经 Java 表构建与 JNI 大数组搬运）：

| d | ms/rotate | **ms/CMUX** |
|---|---|---|
| 1 | 21.168 | 20.675 |
| 4 | 81.589 | 20.483 |
| 16 | 316.554 | **19.872** |

离散度 **4.0%** ⇒ 成本由 CMUX 主导、与 `d` 无关。
⇒ **每次 CMUX ≈ 19.9 ~ 20.7 ms**（这是最可信的一个数）。

交叉验证：330 单元 × 16 轮 × 20 ms ≈ **106 s**，占 ANSWER 147 s 的 **72%**。

## 3. 白盒剖面（独立 C++，直接调 SEAL）

`cmux_profile.cpp`，N=8192 / 4 素数 / **levels=11** / t=65537，基线 SEAL：

| 组件 | 实测 | 备注 |
|---|---|---|
| `transform_to_ntt`（一组多项式） | **0.72 ~ 0.79 ms** | 经 `Evaluator`，含目标拷贝 |
| `multiply_plain`（密文 × 明文） | **0.147 ~ 0.159 ms** | |
| 构造单项式明文 + NTT | **0.244 ~ 0.276 ms** | ← `multiply_power_of_x` 每次都要付 |
| RGSW 密钥构建（2×levels=22 次 `encrypt_symmetric`） | 38 ~ 47 ms | 与整机 16 键 ≈ 900 ms 量级一致 |

### 3.1 ⚠️ 必须承认：剖面里有一个数不可信

同一份剖面测出 **一次 external_product = 16.4 ~ 28.5 ms**（5 次重复波动很大）。
但整机实测**整个 CMUX 只有 19.9 ms**，而 `cmux()` = `sub` + **2×external_product** + `add`。

⇒ **2 × external_product (33 ms) > 整个 CMUX (19.9 ms)，这是矛盾的。**

我不打算把这个数包装成结论。最可能的原因（未逐条验证）：

1. 我的替身 digits 不是真实分解结果；真实 digits 是小值（平衡 base-2¹⁶ 数字），
   而替身是 `(i+k+row) % 32769`（最大到 32768），precomputed-Montgomery 的
   `multiply_plain` 对**小值**可能走更快的路径。
2. 我的 gadget 行没做 `mod_switch` 降 knob；真实 RGSW 键在 `first_parms_id()`，
   但 SEAL 对相同 parms_id 的乘法可能走了不同分支。
3. 每次 `multiply_plain` 都 out-of-place 新建 `Ciphertext`，而真实代码
   `external_product` 内部有复用；分配/拷贝占比可能不同。
4. 5 次重复本身波动 16.4 → 28.5 ms（**74%**），说明该测量点噪声很大。

**结论：`external_product` 的绝对值这次没测准。** 不拿它做任何论断。

## 4. 从可靠数字能推出的东西

用**可靠**的三个数（NTT 0.77 ms、`multiply_plain` 0.15 ms、单项式构造+NTT 0.27 ms）：

- 一次 `multiply_power_of_x` 的**大部分成本不是乘法**，而是
  "构造单项式明文 + 给它做 NTT"（0.27 ms vs 0.15 ms）—— 即**超过一半**花在准备输入上。
- 一次 `external_product` 需要 `2×levels = 22` 个明文，每个都要
  "填数组 + NTT"：纯准备 ≈ 22 × 0.27 = **5.9 ms**，纯乘法 ≈ 22 × 0.15 = **3.3 ms**。
  ⇒ 准备比乘法贵 **1.8 倍**。
- 盲旋转每次调用 `multiply_power_of_x` 共 `d+1 = 17` 次 ⇒ 17 × 0.27 ≈ **4.6 ms**
  是纯准备开销。×330 单元 ≈ **1.5 s**。

### 4.1 一个可做但收益小的具体优化

`multiply_power_of_x` 每次重建同一个单项式并重做 NTT。
它的入参 `a[i]` 在整个 ANSWER 里是**固定的**（`av[3][16]` 在单元循环外只生成一次），
所以这些 NTT 化单项式**完全可以缓存**。

预估：省掉 17 × 0.27 ≈ 4.6 ms/单元（占 CMUX 的 23%？不，这是**按单元**不是按 CMUX）——
按单元算是 4.6 ms，占单元 316 ms 的 **1.5%**。
⇒ **收益约 1.5%，太小，不值得动。**

（这里我把先前"值 0.8%"的估算更新为 1.5%，依据是本次实测的 0.27 ms 单项式成本
与每单元 17 次调用。）

## 5. 由 20 ms/CMUX 反推未被解释的部分

一次 CMUX（按真实代码）= `sub` + 2×external_product + `add`。
用可靠的库操作数去凑：22 次准备(5.9) + 22 次乘法(3.3) = 9.2 ms **每个外积**，
两个外积 18.4 ms —— 已经接近整个 CMUX 的 19.9 ms。

⇒ **这说明 `decompose`（我们自己的多字 CRT 代码）的贡献无法从这个算术里分离出来**，
因为库操作本身就把 19.9 ms 解释掉了。

于是有两种可能，**目前分不清**：
- (A) 库操作（准备 + multiply_plain）就是全部，`decompose` 占比小；
- (B) 真实 digits 是小值 ⇒ 真实的 multiply_plain 更便宜 ⇒ 空出来的时间才是 `decompose`。

**要分清 (A)/(B)，唯一办法是直接给 `decompose` 加计时**（往 C++ 里插 `std::chrono`
会引入 `libwinpthread` 依赖并让 JVM 加载失败，所以得用**独立可执行文件**版的原型来测，
不能用 JNI）。

## 6. 下一步建议（按性价比）

| # | 动作 | 预估 | 成本 |
|---|---|---|---|
| 1 | **给 `decompose` 加独立计时**，分清上面 (A)/(B) | 决定后续方向 | 中：要写一个独立可执行原型 |
| 2 | 若 (B) 成立 → 优化 `decompose`（单次 MP 抽取 + 逐数字向量化 + scratch 复用） | 可能两位数百分比 | 高：改核心 + 重新验证逐位一致 |
| 3 | 纯准备优化（缓存 NTT 单项式） | **≈1.5%，不值得** | 低 |
| 4 | MSVC + HEXL | 未知（但这是 SEAL 官方路径） | 很高：要先装整套工具链 |
| 5 | 减少 CMUX 次数（算法层） | 线性收益（已由 d 无关性证明） | 高 |
