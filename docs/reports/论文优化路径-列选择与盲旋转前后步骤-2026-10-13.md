# 论文里的优化路径：读到了什么、哪些能改、哪些改不动（2026-10-13）

> 问题：「那几篇论文你有读吗？有读出什么优化路径吗？包括改算法本身，
> 甚至改列选择和盲旋转之前之后的步骤以契合它们的提速」

**结论先行**：

1. **论文本身没有留给我们任何 CPU 侧的加速路径**。它们提速靠的是「把贵操作搬到离线」
   （18.2× 是对 BKPIR 的**在线**加速，不是单次运算变快）和「用更小的 N」，这两条我们
   都已经吃到极限。
2. **改列选择之前之后的步骤（EXPAND / 打包选择子）是负收益**，实测 +8.5%，
   方向反了 —— 那是**带宽**优化，而我们**算力**受限。
3. **唯一真正能改的是「载荷长度 B_pay」**，而它的驱动量是 `maxSetSize`（每个值被多少关键词共享）。
   **`maxSetSize` 4→3 实测 ANSWER 从 237 s 降到 180 s（−24.0%）；4→2 预计再减半。**
4. **列选择本身不值得一提**：把 C 从 26 砍到 7（−73% 的乘法次数），ANSWER 只动了 1.3%。

### 1.1 论文的实验参数（§5.1，之前没记下来）

- `N = 16384`（我们 8192），`t = 65537`，SEAL BFV，默认配置达到 128-bit 安全
- BFF **每个关键词 3 个哈希位置**，指纹 **40 bit**
- 合取实验 `ε_BF = 2⁻²⁰`
- 机器：**Intel Core i9-14900K**，Ubuntu 22.04，GCC 11.4，OpenJDK 17

> ⚠️ i9-14900K 有 AVX-512。这正是我们两条加速路线（`-march=native`、MSVC+HEXL）
> 都撞死的原因 —— 我们这台 CPU 只有 AVX2（`HEXL_HAS_AVX512DQ/IFMA/VBMI2` 全部 not found）。

### 1.2 CAPE 的 18.2× 是什么意义上的加速

§5.3 + Table 3 读出来的：

| | 设置 | Setup | 在线 |
|---|---|---|---|
| BKPIR | n=128, m=2⁹, Q=3 | 2.77 s | 261.91 s |
| **CAPE** | 同上 | 15.16 s | **450.10 s** ❓ |
| CAPE-C | 同上 | 22.58 s | 450.50 s ❓ |

> ❓ Table 3 的 OCR 列错位，绝对值不可信（正文另有 "Online server time 3.00 s"）。
> 但**正文的定性结论是可信的**：「CAPE 和 CAPE-C 对固定数据库，**在线时间随 Q 几乎不变**；
> BKPIR 随 Q 线性增长。Q=10 时快 6.47×，Q=30 时快 18.89×。」

**⇒ 论文的 18.2× 是「Q 增大时 BKPIR 变慢」换来的，不是单次运算更快。**
我们的 Q=3，正好落在论文自己承认「BKPIR 在最小设置下仍然有竞争力」的区间里 ——
这与我们实测的交叉点 Q\* ≈ 3.95 完全对上。

### 1.3 论文里被我们之前忽略的两个算法细节

1. **载荷第 2 个系数是「值的个数」**，并且**在客户端参与判定**：
   §3.1「the encoded value count determines the returned set V_K」。
   即客户端靠它把补齐到 m 的载荷裁回真实长度 —— 这就是我们 `payload[1]` 的用途，
   我们做对了。
2. **Algorithm 2 第 4–6 行的「加密 Bloom 打分」在 paper 里是服务器侧
   `CtCtMul` + `log ℓ_BF` 次 `CtRotate`**，我们实现成了
   「把候选 Bloom 位放进明文载荷、客户端本地比」。
   这是 P0-3 的另一半，但**对性能是好事**：加密路径要
   `d·log₂ℓ_BF = 16×5 = 80` 次 CtCtMul（每次 ~1.5 ms）≈ 外加 5%，而明文路径是 0。

### 1.4 附录 B（FusePIR-C）读出来的

- `ℓ_c = ⌈log₂C⌉`、`ℓ_r = ⌈log₂R⌉`；
- 列位和行位**都**转成 RGSW（`LWEtoRGSW`），列位展开成 one-hot 选择子，行位直接驱动 BlindRotate；
- **a 分量全部由一个种子 ρ 生成**（seeded-query，抄 Pirouette）⇒ 上传只剩 ρ 和 β。
- **服务器侧没有变便宜**：正文自己说 FusePIR-C 比 FusePIR **慢 3.20×–5.52×**。

**⇒ 这条路已经封死了**：它换的是带宽，代价是服务器算力。我们的瓶颈是算力。

## 3. 实验 A：改列选择的容量参数 R（= 改「列选择之前之后的步骤」）

### 3.1 为什么这是免费的

```
列选择 = k × B_pay × C   次 multiply_plain      <- 随 C 线性
盲旋转 = k × B_pay × d   次 CMUX                <- 与 C 无关
```

P 表按 `[C][B_pay][N]` 索引，**R 根本不进任何乘法** —— 行选择只是旋转位移量 β。
所以 R 只有一个作用：决定每列能放几个 cell，从而决定 C。

**当前几何**（`CapeDemoData.buildTables`，第 163–175 行）：
`cellsPerCol = floor(R / maxValues)`，`C = ceil(kwCount / cellsPerCol)`。
约束只有 `R ≥ maxValues` 和 `rowOf[i] + k ≤ R`。

| R | cellsPerCol | C | 列选择乘法次数 |
|---|---|---|---|
| 16（当前） | 5 | 26 | 3 × 110 × 26 = **8 580** |
| 24 | 8 | 16 | 5 280 |
| 32 | 10 | 13 | 4 290 |
| 48 | 16 | 8 | 2 640 |
| 64 | 21 | 7 | **2 310（−73.1%）** |

### 3.2 实测（`CapeCGridProbe`，N=8192, d=16, k=3, 默认 keywords.json）

| R | C | cellsPerCol | 表内存 | ANSWER ms | ms/unit | 校验 |
|---|---|---|---|---|---|---|
| 16 | 26 | 5 | 178.8 MB | 212 441 | 643.8 | PASS |
| 24 | 16 | 8 | 110.0 MB | 217 602 | 659.4 | PASS |
| 32 | 13 | 10 | 89.4 MB | 218 817 | 663.1 | PASS |
| 48 | 8 | 16 | 55.0 MB | 211 132 | 639.8 | PASS |
| **64** | **7** | **21** | **36.3 MB** | **213 786** | **647.8** | PASS |

### 3.3 结论：**这条路是死的**

C 降了 73%（26→7），乘法次数降了 73%（8 580→2 310），**耗时只动了 1.3%（最大 212.4 / 最小 218.8，方向还是反的）**。

原因（和 §2 的剖面自洽）：一个单元的成本里
`decompose`（2×0.6 ms）+ 32 次 `multiply_plain`（32×0.153 ms）+ 32 次 `transform_to_ntt`（32×0.75 ms）
每单元≈ **29 ms** 是与 C 无关的；列选择只加 `C × 0.153 ms`，C=26 时 4 ms、C=7 时 1 ms。
**上限 4~5%，实测被噪声吃掉。**

> ✅ 副产品：`R=64` 把**表内存从 178.8 MB 压到 36.3 MB**（C 变小，表按 `[C][B_pay][N]` 缩），
> 全部 PASS 逐位一致。如果要做**内存/缓存优化**，这才是它的价值，不是速度。

## 4. 实验 B：改载荷长度 B_pay（= 真正有效的那一条）

### 4.1 B_pay 的驱动量

```
B_pay = 2 + maxValues × (1 + ℓ_BF)
ℓ_BF  = min_h ⌈ −h · maxSetSize / ln(1 − ε_BF^(1/h)) ⌉
```

`maxSetSize` = **每个值被多少个关键词共享**（= 关键词 Bloom 过滤器里那个值的元素个数），
由 `build_dataset.py` 的 `--max-set-size` 控制（第 102 行 `if len(movie_kws[mv]) < max_set_size`）。

⚠️ 旧计划书里 `predicted ANSWER` 用的 `583 ms/CMUX` 是**过时数**（那是更早的血统，
后来实测是 20 ms/CMUX），报告里所有 "192 000 ms" 之类的预计值都偏大约 3 倍，别再引用。

### 4.2 同 JVM A/B（消掉跨进程漂移，R=16 与当前库同几何，逐位校验）

| 数据集 | maxSetSize | ℓ_BF (h) | B_pay | units | 表内存 | ANSWER ms | ms/unit |
|---|---|---|---|---|---|---|---|
| `keywords.json`（当前） | 4 | 35 (6) | 110 | 330 | 178.8 MB | **237 064** | 718.4 |
| `kw_mss3.json`（新） | **3** | **26 (6)** | **83** | **249** | 134.9 MB | **180 153** | 723.5 |

**⇒ 实测 −24.0%，而单元数正好 −24.5%。**
两个已完成的独立对照：

| 对照组 | 330 units | 249 units | 实测降幅 | 理论降幅 |
|---|---|---|---|---|
| 同 JVM 3 次取最快 | 237 064 | 180 153 | **−24.0%** | −24.5% |
| 同 JVM 1 次 | 209 031 | 178 304 | −14.7% | −24.5% |
| 跨进程（R=64） | 213 786 | 151 223 | −29.3% | −24.5% |

**ms/unit 基本不动**（633–724 之间随机器负载漂移）⇒ **总耗时确实线性 = units 驱动**，
这条杠杆是真的。

### 4.2.1 基线校准（⚠️ 顺手发现旧文档里一个过时数）

把**真实服务**跑了一遍（`CapeDemoService`，N=8192, d=16, 默认库，POST `/api/query`
用池内组合 `06 Oscar Nominated Best Movie - Animation + Tim Burton`）：

```json
{"unitCount":330, "answerMs":241400.6, "queryMs":0.322, "decodeMs":0.099,
 "setupMsLast":1443, "hit":true, "integrity":true, "payloadMismatch":0}
```

- **ANSWER ≈ 241 s**（unitCount=330），与 `CapeCGridProbe` 的 209~237 s 量级一致
  （差值来自机器负载漂移；探针里 ms/unit 在 633~724 之间摆）。
- SETUP 1443 ms（java 323 + native 1120）⇒ **占 ANSWER 的 0.6%**，确认「不必缓存 SETUP」。
- ⚠️ **`CAPE-Native演示前端-实现计划书.md` 和旧 README 里那个「ANSWER ≈145 / 154 s」作废**
  （同文件里 `583 ms/CMUX` 的推算也是过时数）。**当前基线以 241 s 为准。**


### 4.3 还能往下压多少（`build_dataset.py` 实测）

| 关键词数 | maxSetSize | ℓ_BF (h) | B_pay | 相对现在 | 非空对 | 单关键词假阳率 |
|---|---|---|---|---|---|---|
| 128 | **4**（当前） | 35 (6) | 110 | — | 337 | ≈ 5.5% |
| 128 | **3** | 26 (6) | 83 | **−24.5%** | 247 | ≈ 1.1% |
| 128 | **2** | 18 (5) | **59** | **−46.4%** | 136 | ≈ 0.34% |
| 128 | 1 | 9 (5) | 32 | −70.9% | **0** ❌ | — |

- `maxSetSize = 1` **不可用**：每个值只属于一个关键词 ⇒ 任意两个关键词不可能共享值 ⇒
  **组合池空**，合取查询演示直接不成立。（这正是假阳率分析里的 `d ≥ 1` 边界。）
- `maxSetSize = 2` 是可用的最小档：池子还有 **136 对**（前端「随机添加」够用），
  `l_BF=18` 只有 18 bit，**再省 46%**。
- 假阳率按 `(1−e^(−h·n/ℓ))^h` 复核（n=maxSetSize）：
  当前 (35,6,4)=5.5%、(26,6,3)=1.1%、(18,5,2)=0.34% —— **压小 maxSetSize 反而让假阳率更低**，
  是纯粹的免费收益。

## 5. 明确否掉的路径（附实测/文本依据）

| 路径 | 出处 | 为什么否掉 |
|---|---|---|
| **EXPAND 打包选择子** | SealPIR §3.3、FusePIR-C 附录 B | 服务器侧**加**计算换**减**带宽。实测：上传 12→3 个密文，服务器 **+8.5%**（15 288/15 348 → 16 624/16 640 ms）。我们算力受限 ⇒ 方向反了 |
| **`multiply_power_of_X` 走系数域移位** | SealPIR `polyarithsmallmod.h:576` | 我们在 `rgsw_blindrotate.cpp:361` 是 NTT 化 + `multiply_plain`。改掉只省 17 次/单元 × 0.27 ms = 4.6 ms，对 316 ms/单元 = **1.5%** |
| **CAPE-C / FusePIR-C（LWEtoRGSW 选择子展开）** | 附录 B/C | 论文自己说服务器慢 3.20–5.52×；且与 §"不要实现 CAPE-C/FusePIR-C" 的既定决定一致 ⇒ `LweToRgsw` 保持 ⏸ |
| **减 R（行数）** | — | 没有任何收益（R 不进乘法），而 C 会变大 ⇒ 只会更慢 |
| **`-march=native` / `-mavx2`** | 负结果报告 | MinGW-w64/UCRT 的 AVX2 代码生成在本机**崩**（非 JVM 独立 smoke test 也复现） |
| **MSVC + Intel HEXL** | 负结果报告 | 本机 **无 AVX-512**（只有 AVX2），HEXL 收益全在 AVX-512 内核；实测慢 **2.4–2.9×** |
| **减 d（gadget 层数）** | — | **理论上最狠的杠杆**（CMUX 数 = k·B_pay·d），但 `B = 2¹⁶` 被平衡位窗口 `±(t−1)/2 = ±32768` **顶死在恰好边界**，抬到 2³² 要重推全部参数（噪声/模数/安全）。**目前没有安全的重推方案，不动。** |
| **减 k（BFF 位置数）** | CAPE §4.1 | k=3 是 BFF 编码层决定的（论文同款 3 个哈希位置），改它就是改方案本身 |

## 7. 一句话回答你的问题

**读出了什么优化路径？** 只有一条真的：**把载荷变短**，手段是压 `maxSetSize`（4→3 实测 −24%）。
**改列选择和盲旋转的前后步骤有用吗？** 没有 —— 列选择整块只占 1~5%，而且论文给的
「使选择子变紧凑」的所有技巧（EXPAND / 种子化查询 / LweToRgsw）都是**拿服务器算力换带宽**，
在我们这台没有 AVX-512 的机器上是负收益。
**改算法本身呢？** 唯一线性杠杆是 CMUX 个数 `k·B_pay·d`：k 被 BFF 锁死、d 被平衡位窗口锁死、
只剩 **B_pay** —— 所以答案还是压 `maxSetSize`。
