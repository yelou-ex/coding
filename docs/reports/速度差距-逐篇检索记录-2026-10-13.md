## §1 `out_cape_words.txt`（CAPE/FusePIR，`Submission_usenix_232.pdf`）

### 1.1 Algorithm 1 的 ANSWER —— **我们结构逐行对上**

出处 `out_cape_words.txt`（旧件 `out_cape.txt` L872–899，两版一致）：

```
ANSWER(stS, q)
4:  for b = 1 to B_pay do
5:      Acc_{a,b} ← Σ_{c=0}^{C−1} CtPtMul(q^col_a[c], P_{c,b}(X))
6:      Acc'_{a,b} ← BlindRotate(q^row_a, Acc_{a,b})
7:      ct_{a,b} ← SampleExtract_0(Acc'_{a,b})
11:     ct^pay_b ← CtCtAdd(CtCtAdd(ct_0,b, ct_1,b), ct_2,b)
```

⇒ **每个载荷块一次 `BlindRotate`**。我们的 `nativeCapeAnswer` 就是这个循环，
`k·B_pay = 249` 个单元。**结构无误 ⇒ C1~C13 的实现细节之外，没有"算法抄错"这一项。**

### 1.2 SETUP 与 QUERY 的索引分解 —— 也一致

```
SETUP 3: Select public parameters (N, d, t, q)
SETUP 4: Select R, C such that RC ≥ L_BFF, R ≤ N
SETUP 6: y_Ki ← fp(Ki) ‖ m_i ‖ v_{i,1} ‖ ... ‖ v_{i,m} ∈ Z_t^{B_pay}
SETUP 14: P_{c,b}(X) ← Σ_{r=0}^{R−1} D[r + cR][b] · X^r
QUERY 3: u_a ← h_a(K),  r_a ← u_a mod R,  c_a ← ⌊u_a / R⌋
```

我们的 `colOf[i] = i/cellsPerCol`、`rowOf[i] = (i%cellsPerCol)·maxValues` 是同构的。

### 1.3 ⚠️ 论文**没给**的量（⇒ 「论文参数 vs 我们参数」无对照基础）

| 量 | 论文状态 |
|---|---|
| `ℓ_BF` 具体值 | 「ℓ(n, ε_BF)，每次实验内固定」—— **无数值** |
| LWE 维数 `d` | 只在公开参数列表出现 —— **无数值** |
| gadget 底 / 层数 | §2.5 只说「determined by a decomposition base」—— **无数值** |
| `L_BFF` 具体值 | 附录 A 说沿用 ChalametPIR 的参数化 |

⇒ **C0（元原因）成立**：论文没给关键参数，且 Table 3 的 `Time(s)` 是模型输出（§1.4），
所以「达到论文速度」**没有可锚定的定义**。

### 1.4 Table 3 的 `Time(s)` 列（新版提取件已对齐列结构）

新件 L1246–1290，列结构确认为
`n | m | Prep.(s) | Time(s)/Query(MiB) × {Q=3,5,10,20,30} | Resp.(MiB)`：

| n | m | Prep(s) | **Time(s) Q=3** | Time Q=5 | Time Q=10 | **Resp.(MiB)** |
|---|---|---|---|---|---|---|
| 128 | 2⁹ | 15.16 | **3.00** | 3.00 | 3.00 | 441.64 |
| 128 | 2¹⁰ | 29.13 | **3.00** | 3.00 | 3.00 | 845.78 |
| 128 | 2¹¹ | 54.32 | **3.00** | 3.00 | 3.00 | — |
| 256 | 2⁹ | 16.39 | **3.00** | 3.00 | 3.00 | — |
| 512 | 2¹¹ | 324.32 | **3.00** | 3.00 | 3.00 | — |

**两个独立证据说明 `Time(s)` 不是实测：**
1. 与 n、m、Q **全部无关**，而论文自己的复杂度写 `O(n·m·(1+ℓ_BF))`；
2. **响应高达 441~2388 MiB**，检索并盲旋转 441 MiB 的密文不可能只用 3 秒。

> 顺带订正：旧件里我把 `n=128,m=2⁹` 读成「CAPE 15.16」；

### 1.5 可用的副产品：响应体积口径

`Resp.(MiB)`：BKPIR = 1802.11（n=128,m=2⁹），CAPE = 441.64 ⇒ 比值 4.08 ≈ `|V|/m`，
与「BKPIR 的 `|V| = 64m`、CAPE 是 `O(m)`」吻合。**这条口径我们演示里没对过，可留作对照。**

## §3 `out_onionpir_words.txt`（OnionPIR，CCS'21）—— **两条可直接落地的解法**

### 3.1 🎯 解法一：CRT 表示替代多字算术（针对 C1）

> "We implemented OnionPIR atop the SEAL Homomorphic Encryption Library. SEAL only
> provides a BFV encryption scheme. So we implemented RGSW and external products in SEAL.
> **We also implemented the CRT representation of RGSW encryption, which is more efficient
> than using multi-precision arithmetic operations.**"

### 3.2 🎯 解法二：换 NTT 实现（针对 C2）

> "In SEAL the polynomial multiplications are performed using number-theoretic
> transformation (NTT). Each NTT operation has a complexity of n log n... However,
> **we notice that the NTT implementation in SEAL is quite slow**, which hurts the
> computation time of our protocol. Thus, for NTT, we instead use **NFLlib**, an efficient
> library that uses several arithmetic optimizations and **AVX2 specialization** for
> arithmetic operations over polynomials. **The NTT implementation in NFLlib is 2−3×
> faster than SEAL.** We integrated NFLlib's NTT into SEAL. In total, our modifications
> consist of around **3000 lines of C++**."

**机器条件**：「c5.2xlarge instance with 32GB ram and 8 CPU cores with **AVX** enabled」
⇒ **只需要 AVX2，不需要 AVX-512。我们这台机器有 AVX2。**
⇒ 这解释了为什么 `-march=native`（崩）与 HEXL（慢 2.4×）两条路的结论**不能推出 NTT 无解**。

### 3.3 OnionPIR 自己的实测（用于量级校准）

> "for a database with **16 million entries, the server computation time is around 1.7 hours**"
> "the **dot-products account for most of the server computation**"
> "for both SealPIR and OnionPIR, **the computation time increases linearly with the
> database size**"

以及 OnionPIR 表（SealPIR 在 c5.2xlarge 上）：

| 库大小 | QueryUnpack (s) | **Dot-Products (s)** | Total (s) |
|---|---|---|---|
| 2¹⁶ | 5.4 | **20.7** | 26.1 |
| 2¹⁸ | 10.7 | **91.2** | 101.9 |
| 2²⁰ | 21.5 | **381.6** | 403.1 |

⇒ 2¹⁸→2²⁰ 是 4× 记录数、**4.18× 时间**，严格线性 ⇒ 每记录成本恒定可外推。

## §4 `out_pirouette_words.txt`（Pirouette）—— **C15 的出处 + 两条新解法**

### 4.1 🎯🎯 **盲旋转次数：249 vs ~15**（这条是「慢这么多」的结构性根因）

出处 L136–151：

> "Conventional bit decomposition based on **programmable bootstrapping** is practically
> constrained to a small precision of **ℓ = 5 bits** and requires **ℓ expensive BlindRotate
> operations**. For practical PIRs, however, the precision **⌈log₂N⌉ ≥ 25** is much higher.
> Our proposed method, as detailed in Section 3.1, supports high-precision bit decomposition
> using **only approximately 3⌈log₂N⌉ / 5 BlindRotate operations.**"

对照：

| | 每次查询的盲旋转次数 |
|---|---|
| Pirouette（N=2²⁵）| **≈ 3·25/5 = 15 次** |
| **我们（CAPE, k·B_pay）** | **3 × 83 = 249 次** |
| SealPIR（ANSWER，不是盲旋转）| **`d` = 2 次密文乘法**（与记录数无关） |

⇒ **C15 成立，且这是算法结构差异，不是参数或实现错误。**
CAPE 的 `BlindRotate` 次数正比于**载荷长度**（`B_pay`），这是它的设计代价
（换来 `O(m)` 响应 + 加密 Bloom 打分可在密文上做）。

### 4.2 Pirouette 的实验参数（L123–131）

> "Our implementation uses a **25-bit plaintext modulus** and **32-bit ciphertext modulus**
> for LWE. This differs from conventional LWE-based applications that typically consider a
> small plaintext modulus of 4 or 5 bits. ... our query **directly encrypts the index idx
> itself, rather than an encoded representation such as a one-hot vector**."

⇒ 两个可借鉴点：
1. **明文模数 25 bit** —— 接近我们的 `t = 2³²`（我们更激进，已饱和）；
2. **查询直接加密索引，不传 one-hot** ⇒ 查询只有 36 B（PRG 压缩后 32 bit）。
   这是**带宽**优化，且由服务器做同态格式转换 —— 与我们「不实现 CAPE-C」的既定决定一致。

### 4.3 🎯 解法三：approximate gadget（针对 C8：层数被 `base < 2t` 绑住）

出处（Table 4 说明，旧件 L1204–1206 已核对，两版一致）：

> "we note that **ℓ_RGSW ≥ ⌈log_{B_RGSW}(Q)⌉ + 1**. This is due to the fact that **we rely on
> an approximate gadget [33, 94] to improve performance.**"

⇒ **层数不必满足「底^层数 > q」**。我们的 `levels = ⌈qBits/baseBits⌉ = 6` 是被
「完全分解」这个下界推出来的；approximate gadget 允许更少层数，代价是额外噪声。
**我们盲旋转后仍有 97 bit 噪声余量**，正好扛得住 ⇒ **这条对我们特别合适，且论文自己没用上。**

### 4.4 ℓ_RGSW 的取值与 Q 的关系

Table 4（旧件已核对）：`B_RGSW = 2²⁴`、`ℓ_RGSW = 8`，N = 2¹¹，log₂(q) = 12。
他们的 `ℓ = 8` 与 `⌈log_{2²⁴}(Q)⌉+1` 一致，说明 Q 远大于 q。

### 4.5 🎯 解法四（未展开，收益最大）：NTRU 型盲旋转，多项式数量减半

出处 L1621–1632（旧件 L1628 起，两版一致）：

> "we note that many subprocedures in Pirouette utilize the blind-rotation technique first
> described in [34]. Recently, several works [21, 64] introduced blind-rotation approaches
> that rely internally on the **NTRU scheme**. The primary advantage of these methods is
> the superior performance in terms of time complexity stemming from that fact that
> **RGSWs samples are replaced by a different type of ciphertext. The latter contains only
> half as many polynomials** and the modified blind-rotation reduces the..."

⇒ **RGSW 换成 NTRU 型密文 ⇒ 多项式数量减半 ⇒ CMUX 的乘法次数约减半（≈2× 收益）。**
引用 [21] = FINAL（CRYPTO'22，NTRU+LWE），[64] = NTRU-v-um（CCS'22）。
**这条是本轮找到的收益量级最大的一条，但需要单独立项核实**（改的是密钥/密文结构，不是参数）。

### 4.6 Pirouette 的实测（量级校准）

> "for a database of size 2²² with 256-bit entries, SimplePIR and Spiral runtimes are
> **20 ms and 500 ms** respectively, whereas **Pirouette and PirouetteH runtimes are
> 16.5 s and 12.8 s**, which are slower by two to three orders of magnitude."

⇒ **盲旋转类 PIR 本身就是秒级**（2²² = 419 万条）。我们 249 次盲旋转 ≈ 102 s，
即 **≈ 0.41 s/盲旋转**；Pirouette 15 次盲旋转 ⊂ 16.5 s（含其它开销），
即 **≤ 1.1 s/盲旋转**（N=2¹¹，比我们小 4 倍）。
⇒ **单次盲旋转成本我们和 Pirouette 同量级；差的是次数（249 vs 15）** —— 与 §4.1 一致。

## §6 `out_chalametpir_words.txt`（ChalametPIR）—— **一条新方向 + 一条硬约束**

### 6.1 实测（L91–95）

> "1 million keys with associated 256B values (1GB in total), ChalametPIR based on FrodoPIR
> achieves **online server runtimes of around 100ms** (on a 2021 Macbook) and response
> sizes of **4kB**. This represents a minimal performance blow-up (**1.08×**)."

⇒ 1GB 数据库、100 ms。**但它是 FrodoPIR（LWE 矩阵）底座，不是 RLWE 盲旋转**，不可直接搬。
不过它证明了一件事：**关键词 PIR 不必走盲旋转就能到 100 ms 量级** ——
这是「CAPE 的算法选择本身代价很大」的又一个旁证。

### 6.2 🎯 新方向：Binary Fuse filter 替代 Bloom（**但有一条硬约束**）

> L146–148: "implementation of the ChalametPIR scheme, based on FrodoPIR ... and
> **Binary Fuse filters**. ... set **1.08 ≤ c ≤ 1.13, dependent on the choice of k ∈ {3,4}**,
> which appears to be notably smaller than any other filter"
> L297: "such as the novel **Binary Fuse filters** [40]. Binary Fuse filters in particular, ..."

对比我们的 Bloom：`ℓ_BF = 26` bit/值（`ε_BF=2⁻⁶`, `maxSetSize=3`, `h=6`）。
Binary Fuse 的膨胀因子是 **1.08~1.13 倍 n** ⇒ 空间上**小一个数量级**。

**若能替代，`B_pay = 2 + maxValues·(1+ℓ_BF)` 会从 83 掉到 ~30 ⇒ 盲旋转次数 −64%。**

⚠️ **硬约束（`[推断]`，但逻辑清楚）**：CAPE 的加密打分依赖 **Bloom 的可加性**
（`ct_score ← CtCtMul(q_BF, ct_BF)`，得分 = 内积 = 计数交集，与 `0/1` 部分和分布无关）。
Binary Fuse 是**异或型**（每个键命中 3 个位置、靠 XOR 恢复），
`1` 的位置分布**依赖该值关联的关键词集合**，不是「每个关键词独立置 h 位」。
所以**不能直接替换**，需要重新设计同态合取判定 ⇒ 这是**改算法**，不是调参数。

> 佐证：CAPE 附录 A 明确说 BFF 的 `s`/`L_BFF` 沿用 ChalametPIR 的参数化 ——

## §12 `mpc4j/mpc4j-native-fhe/tfhe/` —— **C3 / C4 / C5 的实证解法**

这是 CAPE 说的「native homomorphic encryption routines」的实际代码所在。

### 12.1 参数（`tfhe/params.h` 全文）

```cpp
struct targetP {
    static constexpr size_t l_ = 7;        // 层数 = 7
    static constexpr size_t digits = 124;  // 模数位数
    static constexpr size_t Bgbit = 16;    // gadget 底 = 2^16
    static constexpr uint64_t Bg = 1 << Bgbit;
};
```

**注意**：`Bgbit=16`，`l_=7`，`digits=124`。
而 **`16 × 7 = 112 < 124`** —— **不满足「底^层数 > q」**。
⇒ 🎯 **这就是 Pirouette §4.3 说的 approximate gadget，在论文血统的代码里实实在在用了。**
⇒ **C8 的解法在这里得到代码级确认**，不是只有论文一句话。

### 12.2 🎯 **C1 的解法：`CRTDecPoly` —— 逐素数 + 单字进位链，从不构造多字整数**

`tfhe/rns.h` 的 `CRTDecPoly`：

```cpp
// 逐素数乘 Qinv（一项预处理）
for (i < coeff_modulus_size) for (j < poly_degree)
    poly[j + i*D] = multiply_uint_mod(poly[j + i*D], Qinv[i], coeff_modulus[i]);
// 然后按"混合基"直接取 16 位 digit，进位链在 __uint128_t 里
for (j < poly_degree) for (i < coeff_modulus_size) {
    __uint128_t prod = 0;
    for (k < Qword) {
        prod += (__uint128_t)poly[j + i*D] * Qrst[i][Qword-1-k] + crtdec[Qword-1-k][j];
        crtdec[Qword-1-k][j] = prod & mask;   // mask = 2^16 - 1
        prod >>= Wlen;                        // Wlen = 16
    }
}
```

**关键差别**：`prod` 是 `__uint128_t`（**单字宽**），进位就地右移。
**它从不把 CRT 分量重组成一个 174 位的多字整数。**

对照我们的 `crtComposeMw` + `decomposeValueMw`：
我们先 `mwAddMulWord`/`mwMulWord` 逐级重建**完整的 5 字大整数**，
再 `mwShiftRight16`+`mwAddOne` 做平衡位提取 —— **两趟多字运算**。
本机实测占 CMUX 的 **26.8%**。⇒ **这就是要替换掉的那块。**

### 12.3 🎯 **C3 的解法：一次 NTT 广播到所有素数**

`tfhe/tfhe.cpp` 的 `ExternalProduct_internal`：

```cpp
for (k < 2) for (i < targetP::l_) {
    for (j < poly_degree) for (l < coeff_modulus_size)
        decntt.data(1)[j + l*poly_modulus_degree] = crtdec[k][i][j];   // 同一 digit 广播到所有素数
    util::ntt_negacyclic_harvey_lazy(decntt_iter, coeff_modulus_size,
                                     ...->small_ntt_tables());          // 一次算全部素数
    util::dyadic_product_accumulate(decntt_iter, data_iter0, coeff_modulus_size, res_iter0, prod_iter0);
    util::dyadic_product_accumulate(decntt_iter, data_iter1, coeff_modulus_size, res_iter1, prod_iter1);
}
```

**每层只做 1 次 NTT**（`coeff_modulus_size` 个素数一起）。

对照我们（`rgsw_blindrotate.cpp` 的 `external_product`）：每 (层, 行) 一次
`c->evaluator->transform_to_ntt_inplace(pt, parms_id)`，即 **`2·ℓ` 次**，
而且每次走 `Evaluator`（含目标拷贝与校验）。

⇒ **两处差别：次数减半（C3）+ 绕过 `Evaluator` 直调 `util::`（C5）。**

### 12.4 🎯 **C4 的解法：延迟归约**

`tfhe/util.cpp`：

```cpp
// dyadic_product_accumulate：不归约，累加进高字
multiply_uint64(get<0>(I), get<1>(I), z);
get<3>(I) += z[1] + add_uint64(z[0], get<2>(I), &get<2>(I));
// dyadic_coeffmod：最后一次性 Barrett 归约
```

⇒ **乘法不做模归约，把 128 位积的高/低字分别累加，最后统一归约一次。**
我们每次 `multiply_plain` 都由 SEAL 内部自行归约（无法控制）。

### 12.5 C7 的旁证：它同时提供 HEXL 路径

`tfhe.cpp` 里 `ExternalProduct` 有两个版本：`#ifdef SEAL_USE_INTEL_HEXL` 与 `#else`，
**HEXL 版用 `util::ntt_negacyclic_harvey_lazy` + `dyadic_product_coeffmod`**。
⇒ 与我们实测「HEXL 在本机慢 2.4×」不矛盾：那条路径只在有 AVX-512 时才该开。

### 12.6 另一发现：`mpc4j-crypto-fhe-seal` 是 **SEAL 的 Java 移植**

`mpc4j-crypto-fhe-seal/src/main/java/.../seal/` 下有完整 Java 版 `Evaluator`/`NttTool`/
`GaloisTool`/`RnsTool`/`PolyCore`/`UintArithmeticSmallMod` 等。
⇒ 论文说「MPC4J framework **with native homomorphic encryption routines**」，
说明作者**没有用这个 Java 移植**，而是用 `mpc4j-native-fhe` 的 C++。
**这不改变我们的结论**（我们本来也是 C++），但解释了「为什么论文的 Java 框架不影响它的性能」。

### 12.7 `mpc4j-native-fhe/pir/std/` —— 7 个 oblivious-expansion 后端，可作对照实现

`seal / onion / xpir / vectorized / mul / fast / cw` 各一份 native 实现
（`*StdIdxPirNativeUtils.cpp`），加上 `kw_pantheon`（关键词 PIR）与
`ks_labelpsi`。⇒ **若要做 EXPAND 或对照 NTT 工艺，这里有现成的 C++ 可读。**

### 14.2 `pir/std/..._kw_pantheon_...cpp` —— 关键词 PIR，**与 CAPE 同族但不同路线**

它做关键词匹配用的是**多项式求值**，不是盲旋转：

```cpp
#define MOD_SWITCH_COUNT 9
// 先降模数再进乘法链（控噪声）
for (k = 0; k < MOD_SWITCH_COUNT; k++) evaluator.mod_switch_to_next_inplace(one_ct);
evaluator.sub_plain(expanded_query, db, sub);
for (uint32_t k = 0; k < 16; k++) {           // x^2 -> x^4 -> ... -> x^65536
    evaluator.square_inplace(sub);
    evaluator.relinearize_inplace(sub, relin_keys);
}
for (k = 0; k < MOD_SWITCH_COUNT; k++) evaluator.mod_switch_to_next_inplace(sub);
evaluator.sub(one_ct, sub, result);
```

**判断：不能用来替 CAPE。** 这是「相等检测」（`x^N` 只要 N ≥ 最大距离就置零），
而 CAPE 的加密 Bloom 打分要的是**汉明计数的可加部分和**，不是单点相等。
⇒ 记录为**「同族但不可移植」**，避免以后重复挖。
**可借的只有一条工艺**：进乘法链前先 `mod_switch` 降模数。

### 14.4 🎯🎯 `index_pir.cpp` 的 `poc_decompose_array` —— **C1 的正解（已核实可落地）**

```cpp
void poc_decompose_array(uint64_t *value, uint32_t count,
                         std::vector<Modulus> coeff_modulus, uint32_t coeff_mod_count) {
    if (coeff_mod_count > 1) {
        for (i < count) {
            for (j < coeff_mod_count) {
                uint64_t temp[2]{0, temp_array[(i * coeff_mod_count) + coeff_mod_count - 1]};
                for (uint32_t k = coeff_mod_count - 1; k--;) {
                    temp[0] = temp_array[(i * coeff_mod_count) + k];
                    temp[1] = seal::util::barrett_reduce_128(temp, coeff_modulus[j]);
                }
                value[(j * count) + i] = temp[1];
            }
        }
    }
}
```

**它用 2 字临时量把任意宽整数直接归约到每个素数**，`coeff_mod_count` 次 `barrett_reduce_128`。
**从不构造多字大整数。**

**而 SEAL 自己的 `RNSBase::decompose_array`（`rns.h:79`）是多字版**
（`value` 是 `count × limbs` 个 limb）。⇒ MPC4J 的 `poc_` 版是**单字特化版**，
对我们 `q = 174 bit`（≤ 2 limb）的情形更合适。

**✅ 可落地性已核实：**

| 要素 | 状态 |
|---|---|
| `seal::util::barrett_reduce_128` | ✅ 公开（`uintarithsmallmod.h:167`），输入 `const T *`、输出 `uint64_t` |
| 为什么只用 2 字就够 | ✅ CRT 分量 `r_i` 先重心化到 `(−p_i/2, p_i/2]`（我们的 `crtComposeMw` 已经在做重心化），和 `≤ Σp_i/2 = q/2 ≈ 2¹⁷³`；**平衡进位链每步只按 `≪16` 缩小 ⇒ 临时量恒为 2 字** |
| 我们现在每系数的算术量 | `crtComposeMw`：`4× (mwModWord + mwAddMulWord + mwMulWord)`；`decomposeValueMw`：`6× (mwShiftRightBits + mwAddOne)` —— **两趟 5 字多字运算**（L208/L232/L235/L236） |
| 目标改法 | 逐素数重心化 → 进位链（`__uint128_t`）→ 逐素数 `barrett_reduce_128` |

**⇒ C1 从「文献方向」升级为「已核实可实现」。** 预期打掉 CMUX 的 **26.8%**（实测该占比），
验证方式是改完跑 `CmuxBreakdown` 对比四段占比。

### 14.5 `multiply_power_of_X` 的系数域写法 —— **我们实测过不值得，此处补记原因**

MPC4J（`index_pir.cpp`）走系数域内存移位，**不做 NTT**：

```cpp
seal::util::negacyclic_shift_poly_coeffmod(encrypted.data(i) + (j * coeff_count),
                                           coeff_count, index, parms.coeff_modulus()[j],
                                           destination.data(i) + (j * coeff_count));
```

我们的 `rgsw_blindrotate.cpp:361` 是 `Plaintext mono(n)` + `transform_to_ntt_inplace` + `multiply_plain`。

**但换过去对盲旋转不利**（这一点要写清楚，否则以后会重复尝试）：
`blind_rotate` 里 `cur` 必须留在 NTT 域（否则下一轮 `multiply_plain` 要转回 NTT）。
用系数域移位省下 1 次 `multiply_plain`（0.52 ms）+ 1 次单项式 NTT（0.26 ms），
但要补 1 次正向 NTT（≈0.72 ms）⇒ **≈ 打平**。
⇒ **MPC4J 能这么写，是因为它的 `expand_query` 在系数域进出，不在 NTT 域循环里。**
（我们此前估的「只省 1.5%」与此一致。）

### 14.6 `plain_decomposition` —— **不是 C1 的解法**（避免误记）

`index_pir.cpp:237` 的 `plain_decomposition` 看着像"分解"，但
`total_bits = plain_modulus.bit_count()` —— 它分解的是**明文模数 t**（用 `right_shift_uint128`），
服务的是**查询明文的位分解**，不是我们的密文系数分解。
⇒ **明确排除，不要误当成 C1 的替代。**

### 14.7 🎯 三个密文分解的实现都找到了（7 个后端全扫完）

`index_seal` / `index_xpir` 的响应阶段都调
**`decompose_to_plaintexts(parms, ct)`**（定义在 `index_pir.cpp:19`）：

```cpp
const auto pt_bits_per_coeff = (uint32_t) log2(parms.plain_modulus().value());
const uint64_t pt_bitmask = (1 << pt_bits_per_coeff) - 1;
for (poly_index < ct.size())
  for (coeff_mod_index < coeff_mod_count) {
      const double coeff_bit_size = log2(parms.coeff_modulus()[coeff_mod_index].value());
      const uint32_t local_expansion_ratio = ceil(coeff_bit_size / pt_bits_per_coeff);
      uint32_t shift = 0;
      for (i < local_expansion_ratio) {
          for (c < coeff_count)
              (*pt_iter)[c] = (ct.data(poly_index)[coeff_mod_index*coeff_count + c] >> shift) & pt_bitmask;
          ++pt_iter; shift += pt_bits_per_coeff;
      }
  }
```

**它把每个素数的系数「独立地」按 `t` 的位宽切片，完全不跨素数重组。**

**⚠️ 但它不能照搬到我们身上 —— 这是一条硬结构差异，不是疏忽：**
SealPIR 用**单个大素数**作系数模数（`q = 2⁶⁰ − 2¹⁸ + 1`，见 §2.2），
所以 `q` 就是一个 60-bit 素数、`⌈60/23⌉ = 3` 片就够了，**低位截取即完整分解**。
而我们 `q = Π`（4 个素数、174 bit），且 **`t = 2³²` 只比 `base = 2³²` 大一点** ⇒
我们是在一个**定长窗口**里表示数字，**跨素数的信息必须保留** ⇒ **必须精确还原 `x`**。

⇒ 所以对 C1 真正可用的是 §14.4 的 **`poc_decompose_array` 式「2 字临时量逐素数归约」**，
而不是 §14.7 的「逐素数低位截取」。两条要分清，否则会写出一个静默算错的版本
（我们在 `decomposeValueMw` 上已经吃过一次这种亏，见 §12.1 的 `mwShiftRight16` 记录）。

### 16.4 ⏸ D2（加密打分）为何暂不做 —— 一条技术冲突，不是偷懒

论文 A2 L878-879 的核心是

```
ct_score,j ← CtCtMul(q_BF, ct_{B^F_j})
for r = 0 to log₂ℓ_BF − 1: ct_score,j ← CtCtAdd(ct_score,j, CtRotate(ct_score,j, 2^r))
```

内积 → 汉明权重这一步**要求 Bloom 位处在批处理槽里**（`BatchEncoder` 把向量铺进槽）。

但 BFF 的三路重建（A1 L899 `CtCtAdd(ct_0b, ct_1b, ct_2b)`）要求三路**同槽位对齐**；
而我们的 `ct_{B^F_j}` 是载荷里第 j 个值的 ℓ_BF 个**系数**，`SampleExtract_0` 只给常数项 ——
要把 ℓ_BF 位搬进槽，需要每次 `CtRotate + SampleExtract`（ℓ_BF=26 ⇒ 26 次/值/路），
代价可能超过它能省的。**这与 `缺陷总表 P0-3` 记的是同一堵墙。**

⇒ 结论：D2 不是「实现一下」的量级，它要求重新设计载荷布局（把 Bloom 位放进槽域）
与三路对齐方式。**在 sealed 正确性修完之前不动它**（否则连基线口径都不稳）。

### 17.4 ❌ 否定：C1「照搬 MPC4J 逐素数单字分解」在本参数下不成立

§14.4 曾把「`poc_decompose_array` 式 2 字临时量逐素数归约」写成
**「已核实可实现」**。**这个结论是错的，此处下修。**

根因：MPC4J 能全程用 `__uint128_t` 单字临时量的**前提是它 `q ≤ 2¹²⁴`**
（`tfhe/params.h: digits = 124`），正好放得进一个 128 位字。
**我们 `q = 174 bit`** —— Garner 递推里的加数 `t·Π_{i<j}p_i` 中间值最多 3 个字，
放不进单字临时量。所以那条路**在我们的参数下不存在**。

我按这个思路写过两版实现，**两版都在推导阶段就被自己推翻**（没有落进仓库）：

1. 第一版在「逐素数权重累加」里用 `r[i] != res[i]` 判断负号 —— 重心化后
   `r[i]` **无法单独判断符号**，逻辑无效；
2. 第二版想用「x mod base 与 x mod 各素数两个域同步更新」，但 Garner 递推的加数
   需要 `Π_{i<p}p_i` 的**精确值**（跨多个字），同样回到多字。

⇒ **C1 作为「逐素数化」这条路关闭。**

### 17.5 ❌ 否定：C1 的第二条路（Barrett 替换 128 位除法）实测**大幅变慢**

仍然成立的观察是：`mwModWord` 内层 `v % p`（`v < 2^108`）会编译成 **128 位除法**，
而调用量很大（每系数多次 × 8192 系数 × 每次分解）。所以试了「换成
`seal::util::barrett_reduce_128`（预计算倒数 + 乘法）」。

**实测结果相反**：

| DLL | N=8192 d=16 一次盲旋转 |
|---|---|
| pre-C1（C6 版） | **312.6 / 315.9 ms**（19.54 ms/CMUX），正常完成 |
| Barrett 版 | **> 300 s 未完成**（超时杀掉） |

**解释**（反直觉但站得住）：x86-64 的硬件 128÷64 除法在这颗 CPU 上约 20~40 周期，
而 Barrett 的 3~4 次 64×64→128 乘法 + 移位在**这种小范围**（`v < 2^108`、
`p < 2^44`）下并不更快 —— 教科书上「除法慢、用乘法代替」的经验在这里不成立。

**已回滚**（`git checkout` 源 + 重新构建 DLL 以保证源与二进制一致），
回归 `4 PASS / 0 FAIL`，19.54 ms/CMUX 回到基线。
