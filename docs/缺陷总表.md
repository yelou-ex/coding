## 一、🔴 P0 —— 不修就不能称"实现了 CAPE"

### P0-1　行索引不是论文的 LWE（无噪声 + 编码不兼容）　【**仍未修 · 最大的一条**】

| | |
|---|---|
| **现象** | `CapeEndToEnd4.java:242` 手工算 `q.beta[a] = floorMod(⟨a,s⟩ + r_a, 2N)` —— **没有 `Δ` 缩放、没有误差 `e`**。而通用 `LWE.encrypt`（`lwe-java/cape/he/LWE.java`）按 `b = ⟨a,s⟩ + Δ·m + e (mod q)`、`Δ = q/t` 编码。**两套约定不兼容**：把通用 LWE 密文直接喂盲旋转，旋转量会变成 `Δr = 256r`，而不是 `r`。 |
| **后果 1** | **正确性只在 `e=0` 下成立。** `BlindRotateOps` 自己注明：`e=±1` 就会把行号整体推偏一格、取到相邻记录（实测严丝合缝等于 `p[r+e]`）。 |
| **后果 2** | **安全性一条都不能引。** `b = ⟨a,s⟩ + r` 不满足 LWE 噪声模型；`d=16`、`q_L = 2N` 下攻击者拿到 `(a,b)` 解线性方程组即可恢复 `s`。 |
| **来源** | 审阅 `CAPE-CRYPTO-01` / `CAPE-CRYPTO-02` / 修订版 §1、§4 |
| **修法** | ① 写清 `N, R, q_L, t, Δ, d` 与"行号 → LWE 消息 → 相位 → 旋转指数"的完整映射；② 盲旋转接口显式拒绝不匹配的编码（或在内部做 `Δ` 反缩放）；③ 用论文噪声分布统计误选率，给出可复现的界；④ 覆盖行边界与模数回绕 |
| **状态** | 🔴 **仍存在**（本仓库已记录为偏差 D1，见 `README.md` §3.7、§已记录的偏差） |

### P0-2　客户端 Bloom 查询向量 `b_qry` 构造错误 ⇒ **漏判**

| | |
|---|---|
| **论文** | 算法 2 · QUERY 第 2~3 行：`b_qry ← BF.Gen(0, {K_2,…,K_Q})`、`τ ← ‖b_qry‖₁`。即 `b_qry = OR_{i≥2} B(K_i)`，**只用到关键词**。正确性依赖「**无漏判**」。 |
| **现象 A** | `CapeEndToEnd4` 的 QUERY 段把 `b_v`（该值关联的**全部**关键词的位）或起来，算出的是 `OR_{K ∈ Co(K_2)} B(K)`，其中 `Co(K_2) = ⋃_{v∈V_{K_2}} kw(v)` —— **严格大于** `{K_2}`。`b_qry` 变大 ⇒ `τ` 变大 ⇒ 判定变严 ⇒ **真命中被拒**。 |
| **现象 B** | 该构造遍历的是 `dbValues[idx]`，即**服务器才有的明文值集合**。客户端的 `b_qry` 只能由关键词算出 ⇒ **这段代码不是合法客户端查询**，"能过"只是因为演示里客户端与服务器同在一个 JVM。 |
| **实测反例** | 新增 `BloomQueryConstructionCheck`（真实 `BloomParameters` 代码）：`K_1→{v1,v2}`、`K_2→{v1,v2}`、`K_3→{v1}`，查询 `[K_1,K_2]`。结果 `τ` 从 **5** 变 **12**；真命中 `v2`（`kw=[K_1,K_2]`）论文构造**命中**、演示构造**拒绝** ⇒ **漏判 1 个**。 |
| **来源** | ⚠️ **两份审阅报告都没抓到这一条**（修订版 §8 只提到"单一 `String.hashCode`"）。本仓库 2026-09-29 查出 |
| **修法** | 让演示复用**同一套** Bloom 位函数（`BloomParameters.bits(Collection<String>)`），`b_qry` **只从关键词**算 —— 即把 `BF.Gen` 抽成双方共用的方法。**但要先解决模块可见性**：`BloomParameters` 在 `cape-fusepir-database-handoff`，`rgsw-lab` 的 classpath 看不到它 |
| **状态** | ✅ **已修（2026-09-29）** —— 见 §四。原反例仍可复跑：`cape-fusepir-database-handoff\run.ps1 -Class com.fusepir.database.BloomQueryConstructionCheck` |

### P0-3　Pack 与 Bloom 候选密文没有接在检索密文上

| | |
|---|---|
| **现象** | ANSWER 里构造的 `RingPack` 输入 `asPack/bsPack` 是用**解密后的明文** `ctPay` 现造随机数拼出来的；而且 **`packed` 算完后再无任何引用（死代码）** —— `CapeEndToEnd4.java:353` 赋值，全文无第二处出现。候选 Bloom 密文则由 `ctPay[3..]` 明文**重新加密**（`encryptBloomVector`）。 |
| **后果** | 算法 1 第 13 行与算法 2 的候选响应所需的**真正密文 Pack 并未串入候选评分**。`RingPack`、`BloomScoring` 各自自测再漂亮，也不能推出 CAPE 的同态链路成立。 |
| **实测** | `SampleToPackLink`：`sampleExtract` 输出在 `q_R` 上，喂 `RingPack` 必须先缩放到 `Z_t`，而该缩放引入 `|残差|` 最大 **28**、理论 `std ≈ 15` 的噪声 —— **是 Bloom 位值 1 的十几~几十倍** ⇒ 打包出来的位不再精确，`s_j == τ` 的精确判定不成立 |
| **来源** | 审阅 `CAPE-CRYPTO-04` / `CAPE-CRYPTO-05` / 修订版 §6、§7 |
| **修法** | ① 删掉 `packed` 那段死代码（或真正接进评分）；② 让真实 `ctPaySample`（含实际密钥/模数/噪声）**不解密**直接进入可证明的打包路径；③ 正确做法是让 ring packing **直接在原生模数上做**（按 `q_LWE` 设计 gadget 与缩放交换密钥），而不是「先缩放到 t 再打包」 |
| **状态** | 🟠 **部分已修（2026-09-29）**：`packed` 死代码**已删**、ANSWER 里已显式标注「Pack 未接通」；但**候选 Bloom 密文仍未从检索密文导出**（真障碍是缩放噪声，见 `SampleToPackLink`） |

### P0-4　全流程单 JVM，服务器持有私钥 —— 密钥隔离未验证

| | |
|---|---|
| **现象** | 所有对象挂在同一个 `Mpc4jRgsw m` 上；`Encryptor` / `Decryptor` / `secretKey` 与服务端运算共处一个对象、一个进程。`BloomScoring.decodeScore` 用的也是同一个 `m.decryptor`。 |
| **后果** | 能说明"ANSWER 代码路径不再调用 `decrypt`"，**不能**验证真实客户端/服务器部署的密钥隔离、通信格式，也不能声称"服务器无法解密"。 |
| **来源** | 修订版 §总体结论第 3 条、§7、§9 |
| **修法** | 拆出 client/server 两个类型与两个进程；服务器只给评估材料（`qCol`、`BK`、`q_BF` 密文）；`decodeScore` 只在客户端或自检用 |
| **状态** | 🟠 **部分已修（2026-09-29）**：`Query` 已拆成 `ClientState`（不发）/ `ServerQuery`（发出去）并打印边界；**但进程与密钥仍未隔离**（同一 JVM、同一 `Mpc4jRgsw` 持私钥） |

## 二、🟠 P1 —— 核心链路或转换未闭合

### P1-1　`SampleExtract` 的密钥维度与默认 LWE 参数不匹配，且**密钥切换未实现**

- `LweRlweConversion.java:163` `if (lweParams.dimension != m.n) throw ...` —— 强制 `d == N`（LWE-in-RLWE）。
- 而 `lwe-java` 通用 LWE 默认维数是 512。**两套接口不能互换。**
- 论文 §2.5 允许 SampleExtract 后切到后续计算所用的 LWE 密钥；**该切换未实现**。
- **来源**：`CAPE-CRYPTO-03` / 修订版 §5　**状态**：🟠 仍存在
- **修法**：明确选 `d=N` 还是 `d≠N`；选后者则实现密钥切换并给误差预算；选前者则所有参数/密钥生成/后续运算统一到该维度

### P1-2　LWE ↔ RLWE 转换的舍入误差**没有理论界**（已量化，未给界）

- `extractLwe` 的 `scaleDown`、`switchModulus` 都逐项舍入 `a`、`b`；维数大时各分量误差累加。
- **已做**：`SampleToPackLink` 实测了 `q_R→t` 这一处的噪声（`std ≈ 15`，`N=4096`、三元秘密），与理论 `√(N·2/3)·0.289` 吻合。
- **未做**：其余转换点的最坏界、以及组合（多条相加 + 盲旋转 + 重线性化 + Pack）后的**剩余解码裕量**。
- **来源**：`CAPE-CRYPTO-06`　**状态**：🟠 部分（量级有，界没有）

### P1-3　`RingPack` 的 N=4096 配置**未通过**；输入与 SampleExtract 链路未证明兼容

- `RingPack 4096 32`：**P1 过（槽位解码对），P2/P3/P4 失败**。⇒ **不能把 4096 当作 RingPack+Bloom 的已验证参数**，`N=8192` 才是起步。
- 自检用的是 `Z_t` 上的**合成** LWE 样本，不是 CAPE 主链的 SampleExtract 输出。
- **来源**：`CAPE-CRYPTO-05` / 修订版 §6　**状态**：🟠 仍存在

### P1-4　主演示**只覆盖 `c = 0`**，列 1–3 从未走到

- 三个 BFF 位置是顺序 `pool++`（0..8），而 `R=16` ⇒ `c = u/R` **恒为 0**。
- 负对照（零选择器 / 错位一列）证明"选择器承重"，**但不能替代**对所有列、不同布局、边界行的系统覆盖。
- **旁证**：`SelToExtractBench` 另测了 `c = 0 / 1 / C−1` 的**整列逐系数**对拍（错 0），但那是独立测试，**主演示仍没覆盖**。
- **来源**：修订版 §2　**状态**：✅ **已修（2026-09-29）** —— BFF 位置改成 `u_a = a·R + i` ⇒ `c = a`，实测覆盖列 `[0,1,2]`（C=4）；演示会打印 `[覆盖度]`

### P1-5　主管线里**客户端 Bloom 查询根本不存在**

- `PlaintextFusePirQuery` 只做：重建 payload → 校指纹 → **取值**。`bloomLength` 仅用于算 `groupLength` 以便**跳过** Bloom 段。
- **CAPE QUERY 第 2~4 行（`b_qry` / `τ` / `q_BF`）在 `cape-fusepir-database-handoff` 里完全没有。**
- 全项目只有两份：演示里内联的（**错**，见 P0-2）与 `BloomConjunctionCheck` 的明文参照（对）。
- **来源**：本仓库 2026-09-29 查出　**状态**：✅ **已修（2026-09-29）** —— `PlaintextFusePirQuery` 新增 `bloomQuery(K_2..K_Q)`（返回 `b_qry` 与 `τ`）与 `bloomParameters()`，读 manifest 里的 `bloomHashCount`，用**共享模块**的 `BfGen`

### P1-6　Bloom 参数与论文差距大

| 项 | 论文 | 本仓库演示 | 备注 |
|---|---|---|---|
| `ℓ_BF` | `ℓ(n, ε_BF)`，`ε_BF = 2^-20` ⇒ 约 80~100 位 | **2 位** | τ 判定几乎无区分度 |
| 哈希 | 公开哈希族 `G = {g_1,…,g_h}`，`h ≥ 3` | 演示用 `String.hashCode`，`h=1` | 非密码学、可逆 |
| 指纹 | **40 bit** | 截断 Java 字符串哈希到 1000 以内 | 自洽但与论文不符 |
| BFF 位置 | `h_a(K)` 哈希派生 | 顺序 `0..8` | 未走真 BFF 位置函数 |

**另外**：真实数据子集实测 `ℓ_BF = 5075, h = 16`，**> N = 4096** ⇒ 必须分段，而 `CtCtMul(q_BF, ct^BF_j)` 要求两者都在 N 个槽里。

- **来源**：修订版 §8 / 本仓库偏差 D4~D7　**状态**：🟠 仍存在
- **注**：`BloomParameters` 的参数公式本身**是对的** —— 手算 `maxSetSize=3, ε=2^-6` → 26，实测输出 `h=6, lBF=26` ✓

### P1-7　端到端用**固定种子** `java.util.Random`

- `CapeEndToEnd4.java:119` `Random rnd = new Random(20261013L)` —— 行秘密、LWE `a`、BFF shares、演示数据全部出自它。
- 这是**可复现实验向量**，不是密码学随机源。`lwe-java` 默认可用 `SecureRandom`，但**端到端路径没有采用**。
- **来源**：修订版 §9　**状态**：✅ **已修（2026-09-29）** —— 演示向量用固定种子 `Random`（可复现）、协议密钥（LWE 的 `s`、`a`）改用 `SecureRandom`

## 六、口径问题（不是缺陷，但引结论时必须一起说）
