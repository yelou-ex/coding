feat(CAPE): 把 EXPAND 列选择写入 CapeEndToEnd4 —— 正确性全过，服务端 +8.5%，上传 4x 变小

改动：
- 新增 ExpandOps（从 ExpandProbe 抽出，可复用）：expsFor / keysFor / alphaFor / expand / monomial
- ServerQuery：qCol[k][C] 换成 colMonomial[k]（每条路 1 个单项式 Enc(x^{c_a})）+ expandExps + expandKeys
- QUERY：12 个独立密文 -> 3 个单项式（客户端加密次数同样 12 -> 3）
- SETUP：把服务端的表在【明文侧】折 α = C^{-1} mod t；因为 EXPAND 输出的是 Enc(C)，
  Σ_c CtPtMul(C·1_{c=c*}, α·P_c) = (C·α)·P_{c*} = P_{c*}，密文侧一次 α 乘法都不用
  ⇒ SealPIR Theorem 2 里那个 t 因子（约 16 bit）消失
- ANSWER：每条路先 ExpandOps.expand 一次（在 b 循环外），再走原来的 columnSelect
- recoverAll：负对照改成"改单项式指数"，全零对照退化成 C 个 Enc(0)

实测（N=4096, d=16, C=4, k=3, 120 个单元）：
  正确性：4.1 BFF 重建 / 4.2 指纹 / 4.3 命中 / 4.4 值域 / 4.5 全零负对照 / 4.6 错位负对照
          —— 全部 PASS，恢复 payload 与原始逐位一致
  上传     ：12 个密文 -> 3 个（4x），客户端加密 12 次 -> 3 次
  服务端   ：15 288 / 15 348 ms -> 16 624 / 16 640 ms（+8.5%）

为什么服务端反而慢：扩展要 18 次 applyGalois（C=4 两层：6 次/路 x 3 路），
而 Galois 键切换在这个纯 Java 移植里约 70~80 ms/次 => 约 +1.3 s。
它替掉的东西（C 次密文x明文列选择）本来只占 ANSWER 的约 1%。
=> 与论文原话一致：这是「用服务端额外计算换显著更小的上传通信量」的 trade-off，
   在本地/非带宽受限场景下是净亏。

   基准 CAPE 用 C 个独立 one-hot 密文。属【已记录的偏差】，不是基准行为。
