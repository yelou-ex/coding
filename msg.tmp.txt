feat(route-A): 新增 CapeEndToEndNative —— ANSWER 用 native 的 CAPE 四步端到端，6/6 PASS

新增 rgsw-lab/.../CapeEndToEndNative.java：CapeEndToEnd4 的姊妹版，
结构与它逐项对齐（R×C 二维布局、BFF 三份份额、载荷布局、Bloom 合取判定），
但 ANSWER 整段换成一次 JNI 调用（NativeCapeAnswer.run -> 真 SEAL 4.0.0 C++）。
CapeEndToEnd4.java 一行未改。

注意：4.5/4.6 两条负对照是【新增的】—— CapeEndToEnd4 里它们靠 recoverAll 重造选择子，
本版直接改 c_a / r_a 再跑一次 native，覆盖了列错位与行错位两种。

实测（N=4096, d=16, C=4, k=3, B_pay=40 = 120 个单元）：
  SETUP   : BfGen(h=5, ℓ=18)，R×C=16×4，B_pay=40，BFF 位置 [0,16,32] 覆盖列 [0,1,2]
  QUERY   : c_a=[0,1,2], r_a=[0,0,0]；b_qry 18 位，τ=3
  ANSWER  : native，6120 ms（1 次 JNI 调用）
  DECODE  : 6/6 PASS
    4.1 BFF 三路重建 == 原始 payload（逐位，前 6 个 [70,2,11,0,0,0]）
    4.2 指纹校验（fp=70）
    4.3 合取判定 ⟨b_qry,b_v⟩==τ（得分 3 == τ 3 → 命中）
    4.4 恢复的值 ∈ 明文答案集（第一个值 11）
    4.5 负对照：列错位一列 ⇒ 载荷改变
    4.6 负对照：行错位一行 ⇒ 载荷改变
  速度    : 6120 ms vs 路线 B 15 407 ms => 2.52x

⚠️ 一处实测简化已写进类注释：本版的 Bloom 打分在【明文侧】算（native ANSWER 回环时锚载荷
   已经解出）。同态打分那一版在 CapeEndToEnd4 里已跑通（其 4.3），本类不声称复现了它。
