feat(route-A): native 线走通 —— 多字 CRT 打通论文规模 N=16384，计时收敛

1) 多字 CRT（去掉「最多 2 个工作素数」的限制）
   q 在论文规模下远超 128 位（N=16384 是 8 个素数 / 389 位），所以 CRT 改用
   little-endian 多字数组（MAX_WORDS=16，覆盖到 N=32768 的 881 位）。
   关键简化：digit 底是 2 的幂，所以从多字值里取平衡位根本不需要除法，
   反复 16 位右移即可。
   Garner 逐步合成为 x = r0 + p0*(r1 + p1*(r2 + ...))，
   并用 mwModWord（按字 Horner）算 x mod p_j；
   crt_step_inv[j] 也改成用运行积对 p_j 取模再求逆（原来用 __int128 会溢出）。
   levels 由「对着真实的 q 做 cap*=base 直到 cap>q」定，与 Java 侧 levelsFor 同语义。

2) 持久作业计时（这是唯一能拿到收敛数字的办法）
   原来用两次 nativeSelfTest 求差，两次都重建引导密钥、第一次还付全部冷启动，
   估计值随 K 单调下降（4.66 -> 3.36 -> 2.61）永不收敛。
   现在 nativePrepare 只建一次（引导密钥 + 累加器 + LWE 索引留在 native 内存），
   nativeRunWithCtx 可反复跑并被直接计时。

实测（真 SEAL 4.0.0，与路线 B 同 t/base/位宽口径）：
  规模     素数  q         levels  单轮 CMUX    正确性
  N=4096    2   72 bit       5     2.83 ms      PASS（K=16 与 K=48 收敛，复测一致）
  N=8192    4  174 bit      11    22.0  ms      PASS
  N=16384   8  389 bit      25   213    ms      PASS   ← 论文规模

对照路线 B（MPC4J 纯 Java，N=4096）：优化前 15.55 ms，优化后 6.03 ms
=> native 在 N=4096 上约 2.1x（相对最初 5.5x）。

重要观察：论文规模下 CMUX 比 N=4096 慢 75 倍。原因是结构性的 ——
base 被平衡位窗口 +-(t-1)/2 钉死在 2^16，而 q 有 389 位 => levels = 25，
每轮要做 50 次明文乘 + 50 次明文 NTT。这是「操作数」问题，不是语言问题。
