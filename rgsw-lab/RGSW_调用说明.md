# RGSW 实验层 —— 调用说明

> **位置**：`coding/rgsw-lab/`
> **状态**：已实测通过（两套参数 × **6 项**自检全绿；N=16384 规模检查通过；已启用 NTT 与评估密钥 NTT 域复用）
> **定位**：CAPE/FusePIR 复现中「RGSW 加密 + 外部乘积」这一块的**纯 Java 实验实现**，
> 对应论文 §2.5 的 `RGSW.Enc` 与 `ExternalProduct`。**没有改动论文算法**。
> **重要**：参数已按论文可表达的部分对齐（t、N），但**不具备安全性**，不可用于真实场景。

---

## 一、这是什么

- **RLWE 密文**：形如两个多项式 (c0, c1)，"相位" c0 + c1·s = 缩放后的明文 + 噪声。
- **RGSW 密文**：不是新加密算法，而是**同一份数据 μ 在"不同放大倍数"下的一组密文**（放大倍数 1、B、B²、…），专门用来做**保密的选择**。
- **外部乘积**：把 RGSW 与 RLWE 相乘，得到"μ 乘以原来那份数据"的密文，**服务器全程不需要解密、不需要知道 μ**。

这三样合起来就是盲旋转每一轮要做的事，所以本实验是给盲旋转铺地基。

**这张表直接回答了三个问题：**

1. **为什么必须升级到双素数**：单素数（31 位）下 `base=256` 和 `base=65536` 直接**解密失败**
   —— 噪声超过上限。而论文/MPC4J 的 C++ 实现用的正是 `base=2^16`，**单素数根本放不下**。
2. **基数和余量的取舍**：base 越大 → 层数越少 → 越快，但余量越小。双素数下 base=2^16 仍有 250 万倍余量。
3. **层数比素数个数更影响速度**：`primes=2, base=65536, levels=4` 只要 4.8 ms，
   反而比 `primes=1, base=2, levels=31`（27.4 ms）快——因为多项式乘法次数由层数决定。

## 五、本次新增的关键逻辑：切段前必须先跨素数还原

这是**整个 RGSW 里最容易写错、而且错了不会报错的地方**。

模数由多个素数表示时，一个系数被拆成"各素数下的余数"。要按 B 进制切段，
**必须先把这些余数还原成一个完整的整数**，再切段：

```
对的：  各素数余数  --CRT还原-->  整数 x  --切段-->  x 的各位数字  --> 分别乘 RGSW 分量
错的：  各素数余数  --分别切段-->  两套互不相干的数字              --> 结果静默算错
```

代码里对应 `RingOps.crt()` + `RgswOps.decompose()`，**顺序不能反**。
mpc4j 的 C++ 实现里对应的是 `TFHERNS::CRTDecPoly` 那一段——而 Java 侧原本**没有**这个能力，
所以这块是本实验的实质性产出。

> 本实验用 2 个素数，CRT 还原可以用单个 64 位整数直接算完。
> **素数更多时中间乘积会超出 64 位，必须换成大整数**——正式实现要改这里。

## 六、踩坑记录（七个都真实踩过，且都不报错或报错很晚）

1. **加密与解密必须互为逆**：编码用 `round(m·q/t)`、解码用 `round(相位·t/q)`，
   不能用整数除法取整的 Δ（q/t 的真实值带小数，累计会偏）。
2. **相位不能先中心化再解码**：消息 m > t/2 时编码值本来就超过 q/2，中心化会把它们误判成负数。
3. **切段必须满足 B^l > q**，否则高位丢失、静默算错（已在构造函数里加检查，参数不合法直接抛异常）。
4. **三元密钥的 −1 存成 q−1，不能走"小系数快路径"**：它看着是个接近 2^31 的大数，
   直接累加会溢出。已加三元专用乘法（按符号做加/减，每个累加位置总量 < 2^41，安全）。
5. **算层数时用循环累乘会溢出成死循环**：`cap *= base` 在 cap 超过 2^63 后变成负数，
   循环条件永远成立。**实测表现是"程序跑了 10 分钟没结果"**，改成按位宽直接算层数后，全套测试 1.5 秒完成。
7. **`BigInteger.longValue()` 是有符号截断**：把模数从"单个 64 位"升级到大整数之后，`constant()` 里还留着 `p.q.longValue()`。q 有 451 位时它只取低 64 位，而且**低字最高位为 1 时返回负数**，于是选择器系数变成负数、被归约成 p−4 这种垃圾值——外部乘积全错、但只有 μ=常数 这一路会错。
   **这个坑的排查极快，因为测试用例把范围夹死了**：μ=0 过、μ=X^k 过、只有 μ=1 失败 → 直接指向只有 `constant()` 会碰 q 这个事实。
   **对策**：对可能超 64 位的量一律用大整数取模（`BigInteger.valueOf(v).mod(q)`），不要用 `.longValue()`。

6. **Windows PowerShell 5.1 默认按 GBK 读文本文件**（`.ps1` 和 `.env` 都中招）：
   - `.env` 被错解时，中文注释会**吞掉下一行的键值**（实测 `RGSW_N=1024` 整个消失）；
   - `.ps1` 被错解时，**脚本自身会被解析错**，报出莫名其妙的语法错误、或某些语句静默消失。
   
   **对策**：`.ps1` 一律只用 ASCII 注释；`.env` 用 `ReadAllLines` 显式指定 UTF-8 读取；
   Java 读文件时统一 `StandardCharsets.UTF_8`。

另外，外部乘积里"数字多项式 × 密文多项式"用的是**内层不取模**的快路径
（数字 < B ≤ 2¹⁶、密文系数 < 2³¹，累加 16384 项也只有 2⁶¹，离溢出还差 2²）——
这是实测出来的 6.5 倍提速，且数学完全没变。

### 六之二、改用 MPC4J 的 RLWE 后新增的坑（2026-09-16 实测，全部已修）

把 RLWE 层换成 MPC4J 之后，`Mpc4jRgsw.java` 又踩了三个新坑。它们的共同特征是
**"μ=0 的测试会假通过"**——因为"错的乘数 × 零的加密"仍然是零的加密，所以只有
μ=1 那一路才会暴露问题。测试用例必须包含 **RGSW(1) ⊗ c = c** 这一条。

1. **MPC4J 的私钥是"系数域的三元多项式"，不是 NTT 域**。
   `KeyGenerator` 里是 `RingLwe.samplePolyTernary(..., secretKeyRns.coeff())`，
   直接写进系数数组。所以早期那个"把私钥当 NTT 数组、逐系数乘 g 得到 g·s"的写法必错
   （对系数域数组做逐系数相乘没有数学含义）。**正确做法是根本不碰私钥**：NTT 是线性的，
   把常数 g 加到密文的**第二个分量**上，相位就自动多出 g·s：
   `phase(c0, c1+g) = c0 + (c1+g)·s = phase + g·s`。

2. **明文能无损表达的数字范围只有 `(-t/2, t/2)`，所以切段必须用平衡位**。
   MPC4J 的 `transformToNttInplace(Plaintext, parmsId)` 做的是 fast plain lift：
   先把明文系数按**有符号代表元**嵌进 RNS（`值 ≥ (t+1)/2 = 32769` 的会被当成 `值 − t`），
   再在 Z_q 上做 NTT。t = 65537 时窗口只有 ±32768.5，而无符号位是 `[0, 65536)`——
   凡是 > 32768 的数字都被**静默地当成负数**，外部乘积整体错位（实测 2048 个系数错 2020 个）。
   改成平衡位（每段居中到 `(-B/2, B/2]`）后全部正确，且噪声还减半
   （平衡位属于已发表做法，见 §七）。
   平衡位**不引入近似误差**：只要 `B^levels/2 > q`，逐段平衡展开就是精确的
   （q ≈ 2^54、B = 2^16、levels = 4 → B⁴/2 = 2^63 ≫ 2^54，余项必为 0）。
   代码里已加断言：数字一旦超出明文窗口直接抛异常，不留静默错误。

3. **密文/明文的形式（NTT 域 or 系数域）必须显式统一**，MPC4J 不会自动转换：
   - `Evaluator.add` / `multiplyPlain` 都要求两者**同形式**，否则抛 `NTT form mismatch`
     （实测表现：CMUX(μ=0) 直接异常）；收尾时要在**副本**上转 NTT，别改调用方的密文。
   - 喂给 `multiplyPlain` 的明文必须先用 `transformToNttInplace(pt, ct.parmsId())` 转 NTT。
   - BFV 的 `decrypt` 要求系数域，所以外部乘积的 NTT 结果要能转回来。

另外两条"参数/性能"上的硬约束（不是逻辑坑，但会直接卡住）：

- **`CoeffModulus.create` 会被 128-bit 安全标准拒绝**，要用 `CoeffModulus.bfvDefault(n)`；
  N=1024 只能装约 27 位、噪声会超预算，**N 至少 2048** 才够跑一次外部乘积。
- **MPC4J 的 `AbstractGaloisTool` 每层模数分配 N² 个整数**，素数一多就 OOM
  （N=16384、9 素数 ≈ 1 GB/层）。自研 RLWE 能跑到 15 素数/451 位，MPC4J 到不了——
  这也是"自研实现先别删"的原因之一。

## 七、已应用的优化（附前后实测）

按"采用已发表方案、不自己发明"的原则做了三件事：

| 优化 | 说明 | 出处 |
|---|---|---|
| **NTT 环乘法** | 每个素数上的多项式乘法从 O(N²) 换成 O(N log N)。参数生成时**自动挑 NTT 友好的素数**（满足 2N \| p−1），否则自动回退朴素乘法 | 该领域标准做法，MPC4J 的正式实现里也有 |
| **评估密钥常驻 NTT 域** | 一次查询里同一个 RGSW 会被复用上千次，且全程不变。把它首次使用时算出的 NTT 结果缓存住，之后每次外部乘积只需变换"源密文切段得到的数字多项式" | TFHE 实现的标准做法（避免重复变换评估密钥） |
| **私钥常驻 NTT 域** | 加解密与相位计算都要做"私钥 ⊛ 多项式"，而私钥全程不变。缓存它的 NTT 形式，避免每次加解密都重新变换 | 同上 |
| **CRT 逆元预计算** | 跨素数还原每次外部乘积要调用 2N 次，逆元改在参数构造时算一次 | — |
| **自检兜底** | 新增 **Test 0**：NTT 乘法与朴素乘法**逐位对照**，只要有一处不一致就报错 | — |

同配置下的前后实测：

| 场景 | 优化前 | 优化后 | 倍数 |
|---|---|---|---|
| N=16384、2 素数、base=2¹⁶、l=4，单次外部乘积 | 3.6 s | **0.054 s** | 67× |
| N=16384、1 素数，单次外部乘积 | 8.0 s | **0.15 s** | 53× |
| N=1024，全套自检（原 5 项 → 现 6 项） | 6.5 s | **0.8 s** | 8× |

N=16384、2 素数、base=2¹⁶ 下**各阶段耗时**（私钥 NTT 缓存前后）：

| 阶段 | 修前 | 修后 | 倍数 |
|---|---|---|---|
| RLWE 加密 | 0.483 s | **0.037 s** | 13× |
| 外部乘积 | 0.094 s | **0.054 s** | 1.7× |
| RLWE 解密 | 0.143 s | **0.024 s** | 6× |
| 噪声测量 | 0.131 s | **0.010 s** | 13× |
| 小计 | 0.85 s | **0.13 s** | **6.5×** |

> 这次修的是一个**真瓶颈**：私钥乘法原先走 O(N²) 朴素路径，导致加解密比外部乘积还慢几倍。
> 教训是——**只看"外部乘积快不快"是不够的，要分阶段量**。

**注意**：N 小时 NTT 的优势不明显（N=512 时只有约 3×），因为 NTT 自身的常数开销占比大；
**N 越大收益越大**——而论文的 N 正是 16384。
